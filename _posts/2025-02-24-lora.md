The motivation for LoRA is simple. Pretraining a large model is extremely expensive both in terms of time and resources. Pretraining gives the model general knowledge about the world which is often very different from a specific downstream task. Vanilla finetuning for a specific downstream task requires updating at least parts of the pretrained model which can lead to catastrophic forgetting. On the other hand, most finetuning for a simple downstream task intuitively will happen in a much lower dimension space (low rank) than the whole rank of the pretrained model. The idea of LoRA is attaching low-rank learnable matrices so finetuning the pretrained model can be both performant for the task and also doesn’t lead to catastrophic forgetting. Let’s dive in.

## Linear Algebra Refresher

First, we need a little bit of Linear Algebra refresher,

### The Eckart-Young theorem

Let a matrix $M \in \mathbb{R}^{m \times n}$ have singular value decomposition:

$$M = U \Sigma V^T$$

where:

- $\Sigma = \text{diag}(\sigma_1, \sigma_2, \dots)$
- $\sigma_1 \ge \sigma_2 \ge \dots$

Then the **best rank-$r$ approximation** of $M$ (in Frobenius or spectral norm) is:

$$M_r = U_r \Sigma_r V_r^T$$

i.e., keep only the top $r$ singular values and vectors.

This theorem is quite intuitive. It’s basically saying most information is concentrated (if at all concentrated) in the top dimensions, and preserving those dimensions will result in the best matrix that can preserve that information at the given rank. In this post, we will not derive this theorem but instead connect LoRA to Eckart-Young which in turns proves that LoRA provides the best rank-r approximation of the matrix weight.

First, let’s SVD approximation in pytorch and explore a bit. A bit of setup first so the snippets below run top to bottom,

```python
def low_rank_approx(W: torch.Tensor, rank: int) -> torch.Tensor:
    """
    Best rank-r approximation via truncated SVD (Eckart-Young theorem).
    W = U @ diag(S) @ Vh  ->  W_r = U[:,:r] @ diag(S[:r]) @ Vh[:r,:]
    """
    U, S, Vh = torch.linalg.svd(W, full_matrices=False)
    # Truncate to top-r components
    U_r  = U[:, :rank]           # [d, r]
    S_r  = S[:rank]              # [r]
    Vh_r = Vh[:rank, :]          # [r, k]
    return U_r @ torch.diag(S_r) @ Vh_r

def reconstruction_error(W: torch.Tensor, W_approx: torch.Tensor) -> float:
    """Normalized Frobenius error."""
    return (W - W_approx).norm("fro").item() / W.norm("fro").item()

def explained_variance(W: torch.Tensor, rank: int) -> float:
    """
    Fraction of total spectral energy captured by top-r singular values.
    S^2 = squared singular values = eigenvalues of W^T W.
    """
    S = torch.linalg.svdvals(W)
    return (S[:rank] ** 2).sum().item() / (S ** 2).sum().item()
```

One of the key insights of the LoRA paper ([Hu et al., 2021](#ref-lora)) is that "We hypothesize that the change in weights during model adaptation also has a low 'intrinsic rank'." They build on prior work by [Aghajanyan et al., 2020](#ref-aghajanyan), which showed that pretrained models have a low intrinsic dimensionality — meaning you can fine-tune effectively in a surprisingly small subspace. LoRA's insight is that if the task-specific update $\Delta W = W_{finetuned} - W_{pretrained}$ is low-rank, then we can represent it with two small matrices $B$ and $A$ instead of updating the full weight $W$ directly, which is where all the parameter savings come from.

Let’s confirm this for ourselves,

## Implementation

First, we implement a LoRA linear layer that we’re going to later use to inject / replace the pretrained linear layers with.

```python
class LoRALinear(nn.Module):
    """
    Linear layer with LoRA bypass.
    h = Wx + (alpha/r) * B A x
    """
    def __init__(
        self,
        in_features:  int,
        out_features: int,
        rank:         int   = 4,
        alpha:        float = None,
        bias:         bool  = True,
    ):
        super().__init__()
        self.in_features  = in_features
        self.out_features = out_features
        self.rank         = rank
        self.alpha        = alpha if alpha is not None else float(rank)
        self.scaling      = self.alpha / self.rank
        self.merged       = False

        # Frozen pretrained weight — requires_grad=False
        self.weight = nn.Parameter(
            torch.empty(out_features, in_features), requires_grad=False
        )
        nn.init.kaiming_uniform_(self.weight, a=math.sqrt(5))

        if bias:
            self.bias = nn.Parameter(torch.zeros(out_features))
        else:
            self.register_parameter("bias", None)

        # Trainable LoRA matrices
        self.lora_A = nn.Parameter(torch.empty(rank, in_features))
        self.lora_B = nn.Parameter(torch.empty(out_features, rank))

        self.reset_lora_parameters()

    def reset_lora_parameters(self):
        """
        A ~ kaiming_uniform, B = 0.
        Guarantees delta_W = BA = 0 at init → model starts at pretrained checkpoint.
        """
        nn.init.kaiming_uniform_(self.lora_A, a=math.sqrt(5))
        nn.init.zeros_(self.lora_B)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        base = F.linear(x, self.weight, self.bias)
        if self.merged:
            return base
        # LoRA path: x → A → B, scaled by alpha/r
        lora = F.linear(F.linear(x, self.lora_A), self.lora_B)
        return base + self.scaling * lora

    def merge_weights(self):
        """W ← W + scaling × B @ A  (in-place, zero inference overhead)."""
        if not self.merged:
            self.weight.data += self.scaling * (self.lora_B @ self.lora_A)
            self.merged = True

    def unmerge_weights(self):
        """Undo merge — useful to resume training."""
        if self.merged:
            self.weight.data -= self.scaling * (self.lora_B @ self.lora_A)
            self.merged = False

    def trainable_parameters(self) -> int:
        return self.lora_A.numel() + self.lora_B.numel()

    def extra_repr(self) -> str:
        return (f"in={self.in_features}, out={self.out_features}, "
                f"r={self.rank}, alpha={self.alpha}, merged={self.merged}")
```

The idea is that we’re going to attach a low rank matrix $BA$ to some of the linear layers of the original model. So normally, a linear layer would be $h = Wx + b$, now it becomes $h = (W + BA)x + b$. We will then freeze $W$, so the gradient only flows into the low rank matrices $B$ and $A$. This guarantees that we don’t modify the existing weights $W$ and avoid catastrophic forgetting, but also have effective updates since normal finetuning is low-rank in nature.

Two details in that class are worth pausing on. The first is the `scaling = alpha / rank` factor that multiplies the LoRA path. Why is it there? The magnitude of $BA$ naturally grows with the rank $r$ (more directions summed together), so without compensation, changing $r$ would also change how strongly the adapter affects the output, and you’d have to re-tune the learning rate every time you tried a new rank. Dividing by $r$ (and scaling by a fixed $\alpha$) decouples the two: you can sweep the rank while keeping the effective update magnitude, and hence the good learning rate, roughly stable. A common convention is $\alpha = r$ so the scaling is exactly 1, with $\alpha$ then used as a separate tuning knob.

The second is the initialization. We init $A$ with Kaiming and set $B = 0$, so that $BA = 0$ at the very start and the model begins exactly at the pretrained checkpoint, the adapter contributes nothing until training starts moving $B$ off zero. (One subtlety: the `kaiming_uniform_` on `self.weight` in the constructor is really only there for when `LoRALinear` is used standalone; in the injection path below we immediately overwrite that weight with the pretrained one and freeze it, so that particular init is dead code in our flow. I’m leaving it in since it makes the layer usable on its own.)

We write some code to inject this layer into a toyGPT model. First the toyGPT itself,

```python
@dataclass
class GPTConfig:
    vocab_size: int   = 256
    seq_len:    int   = 64
    n_layers:   int   = 4
    d_model:    int   = 128
    n_heads:    int   = 4
    d_ff:       int   = 512
    dropout:    float = 0.1

class CausalSelfAttention(nn.Module):
    def __init__(self, cfg, linear_cls=nn.Linear):
        super().__init__()
        self.n_heads = cfg.n_heads
        self.d_head  = cfg.d_model // cfg.n_heads
        self.q_proj  = linear_cls(cfg.d_model, cfg.d_model, bias=False)
        self.k_proj  = linear_cls(cfg.d_model, cfg.d_model, bias=False)
        self.v_proj  = linear_cls(cfg.d_model, cfg.d_model, bias=False)
        self.o_proj  = linear_cls(cfg.d_model, cfg.d_model, bias=False)
        self.drop    = nn.Dropout(cfg.dropout)
        self.register_buffer(
            "mask",
            torch.tril(torch.ones(cfg.seq_len, cfg.seq_len)).view(1,1,cfg.seq_len,cfg.seq_len)
        )

    def forward(self, x):
        B, T, C = x.shape
        def reshape(t):
            return t.view(B, T, self.n_heads, self.d_head).transpose(1, 2)
        q, k, v = reshape(self.q_proj(x)), reshape(self.k_proj(x)), reshape(self.v_proj(x))
        att = (q @ k.transpose(-2,-1)) / math.sqrt(self.d_head)
        att = att.masked_fill(self.mask[:,:,:T,:T] == 0, float("-inf"))
        att = self.drop(torch.softmax(att, dim=-1))
        out = (att @ v).transpose(1,2).contiguous().view(B, T, C)
        return self.o_proj(out)

class TransformerBlock(nn.Module):
    def __init__(self, cfg, linear_cls=nn.Linear):
        super().__init__()
        self.ln1  = nn.LayerNorm(cfg.d_model)
        self.attn = CausalSelfAttention(cfg, linear_cls)
        self.ln2  = nn.LayerNorm(cfg.d_model)
        self.ff   = nn.Sequential(
            nn.Linear(cfg.d_model, cfg.d_ff), nn.GELU(),
            nn.Dropout(cfg.dropout),
            nn.Linear(cfg.d_ff, cfg.d_model),
        )
    def forward(self, x):
        x = x + self.attn(self.ln1(x))
        x = x + self.ff(self.ln2(x))
        return x

class TinyGPT(nn.Module):
    def __init__(self, cfg, linear_cls=nn.Linear):
        super().__init__()
        self.embed  = nn.Embedding(cfg.vocab_size, cfg.d_model)
        self.pos    = nn.Embedding(cfg.seq_len, cfg.d_model)
        self.blocks = nn.ModuleList([TransformerBlock(cfg, linear_cls) for _ in range(cfg.n_layers)])
        self.ln_f   = nn.LayerNorm(cfg.d_model)
        self.head   = nn.Linear(cfg.d_model, cfg.vocab_size, bias=False)

    def forward(self, idx):
        B, T = idx.shape
        x = self.embed(idx) + self.pos(torch.arange(T, device=idx.device))
        for block in self.blocks:
            x = block(x)
        return self.head(self.ln_f(x))

    def count_params(self):
        total     = sum(p.numel() for p in self.parameters())
        trainable = sum(p.numel() for p in self.parameters() if p.requires_grad)
        return total, trainable

cfg        = GPTConfig()
base_model = TinyGPT(cfg).to(device)
```


And then the injection logic that walks the module tree and swaps the target linear layers for `LoRALinear`,

```python
def inject_lora(
    model:          nn.Module,
    rank:           int   = 4,
    alpha:          float = None,
    target_modules: list  = ["q_proj", "v_proj"],
) -> nn.Module:
    """
    Replace target nn.Linear modules with LoRALinear in-place.
    """
    # Step 1: freeze everything
    for p in model.parameters():
        p.requires_grad = False

    # Step 2: replace target linear layers
    for full_name, module in list(model.named_modules()):
        # Check if this module's leaf name matches a target
        leaf_name = full_name.split(".")[-1]
        if not isinstance(module, nn.Linear) or leaf_name not in target_modules:
            continue

        # Build the LoRALinear replacement
        lora_layer = LoRALinear(
            in_features  = module.in_features,
            out_features = module.out_features,
            rank         = rank,
            alpha        = alpha,
            bias         = module.bias is not None,
        )
        # Copy pretrained weight over (keep it frozen)
        with torch.no_grad():
            lora_layer.weight.copy_(module.weight)
            if module.bias is not None:
                lora_layer.bias.data.copy_(module.bias.data)

        # Move to same device as the original module
        lora_layer = lora_layer.to(module.weight.device)

        # Navigate to parent and replace child
        parts      = full_name.split(".")
        parent     = model.get_submodule(".".join(parts[:-1])) if len(parts) > 1 else model
        setattr(parent, parts[-1], lora_layer)

    # Step 3: unfreeze LoRA params
    for module in model.modules():
        if isinstance(module, LoRALinear):
            module.lora_A.requires_grad = True
            module.lora_B.requires_grad = True

    return model

lora_model = copy.deepcopy(base_model)
lora_model = inject_lora(lora_model, rank=4, target_modules=["q_proj", "v_proj"])

total, trainable = lora_model.count_params()
print(f"Total params:     {total:,}")
print(f"Trainable params: {trainable:,}")
print(f"Trainable ratio:  {trainable/total:.2%}\n")
for name, p in lora_model.named_parameters():
    if p.requires_grad:
        print(f"  trainable: {name}  {tuple(p.shape)}")
```

## Training the LoRA model

Now let’s actually fine-tune the injected model and confirm the adapters learn something. I’ll use a trivial copy task (predict the next token in a repeating pattern) just to see the loss move, since the goal here is to validate the plumbing, not to train anything useful.

```python
def make_batch(cfg, batch_size=32):
    # toy task: sequences of a repeating pattern the model has to memorize
    pattern = torch.randint(0, cfg.vocab_size, (cfg.seq_len + 1,))
    batch   = pattern.unsqueeze(0).repeat(batch_size, 1)
    x, y    = batch[:, :-1], batch[:, 1:]
    return x.to(device), y.to(device)

optimizer = torch.optim.AdamW(
    (p for p in lora_model.parameters() if p.requires_grad), lr=1e-3
)
loss_fn = nn.CrossEntropyLoss()

lora_model.train()
for step in range(200):
    x, y   = make_batch(cfg)
    logits = lora_model(x)
    loss   = loss_fn(logits.reshape(-1, cfg.vocab_size), y.reshape(-1))
    loss.backward()
    optimizer.step()
    optimizer.zero_grad()
    if (step + 1) % 50 == 0:
        print(f"step {step+1:>3} | loss = {loss.item():.4f}")
```

Note that we only hand the optimizer the parameters with `requires_grad=True`, which after `inject_lora` is exactly the LoRA A and B matrices. Everything else stays frozen. The loss should fall steadily as the rank-4 adapters absorb the task,


(These numbers are illustrative from a toy run, your mileage will vary with the seed and the task.) The takeaway is that 8,192 trainable parameters spread across the q and v projections are enough to drive the loss down, which is the empirical claim LoRA rests on: the useful update lives in a tiny subspace.

## Merging for zero inference overhead

During training the LoRA forward pass computes the base path and the adapter path separately and adds them, which means inference is slightly slower than the original model (two extra small matmuls per layer). But because the adapter is linear, we can fold it back into the weight once we’re done training. That’s what `merge_weights` does: it sets $W \leftarrow W + \tfrac{\alpha}{r} BA$ in place, after which the forward pass is just a single `F.linear` again, identical in cost to the original layer.

The nice property to verify is that merging doesn’t change the output. The merged and unmerged forward passes should be numerically identical (up to floating point),

```python
lora_model.eval()
x, _ = make_batch(cfg, batch_size=1)

with torch.no_grad():
    out_unmerged = lora_model(x)
    for m in lora_model.modules():
        if isinstance(m, LoRALinear):
            m.merge_weights()
    out_merged = lora_model(x)

max_diff = (out_unmerged - out_merged).abs().max().item()
print(f"max abs diff after merge: {max_diff:.2e}")   # ~1e-6, i.e. floating point noise
```

This is exactly why LoRA is so popular for serving: you train a small adapter, merge it once, and ship a model that’s bit-for-bit a normal model at inference time with no latency penalty. And because `unmerge_weights` is just the same operation with a minus sign, you can pop the adapter back off to keep training or to swap in a different adapter for a different task. A single frozen base model can host many merge-on-demand adapters, which is the whole multi-tenant LoRA serving story.

## Why does this work? Connecting LoRA to Eckart-Young

Let’s close the loop on the linear algebra refresher from the start. We saw two things empirically: that the best rank-$r$ approximation of a matrix is its truncated SVD (Eckart-Young), and that fine-tuning updates $\Delta W$ have a rapidly decaying singular value spectrum (low intrinsic rank). LoRA ties these together.

Eckart-Young ([Eckart and Young, 1936](#ref-eckart-young)) tells us that if we want to approximate the *true* full fine-tuning update $\Delta W$ with a rank-$r$ matrix, the best possible choice is the truncated SVD $\Delta W_r = U_r \Sigma_r V_r^T$, and this holds for both the Frobenius and spectral norms. The size of the leftover error is governed by the singular values you threw away: in the spectral norm it’s exactly $\sigma_{r+1}$ (the first discarded singular value), and in the Frobenius norm it’s $\sqrt{\sum_{i > r} \sigma_i^2}$. Either way, if the discarded singular values are tiny, the approximation is excellent. Now look at what LoRA parameterizes: $BA$, where $B \in \mathbb{R}^{d \times r}$ and $A \in \mathbb{R}^{r \times k}$. The product of a $d \times r$ and an $r \times k$ matrix is exactly a general rank-$\le r$ matrix, so the set of updates LoRA *can* represent is precisely the set of all rank-$r$ matrices. That means the best $BA$ LoRA could possibly learn is the Eckart-Young optimum $\Delta W_r$, and we can even write it out: take $B = U_r \Sigma_r$ and $A = V_r^T$ (any factorization of the truncated SVD works) and $BA = \Delta W_r$.

So the chain is: fine-tuning updates are empirically low-rank → the best rank-$r$ approximation of that update is its truncated SVD (Eckart-Young) → LoRA’s $BA$ can represent any rank-$r$ matrix, including that optimum. If the true update really concentrates its energy in the top $r$ singular directions, then a rank-$r$ adapter loses almost nothing, which is why such a tiny number of trainable parameters can match full fine-tuning on many tasks.

One honest caveat worth stating, since it’s easy to over-claim here. Eckart-Young guarantees the optimum *exists* inside LoRA’s representable set, but LoRA doesn’t compute the SVD. It learns $A$ and $B$ by gradient descent on the task loss, so it finds *a* good rank-$r$ update, not provably *the* truncated-SVD update. The two coincide only at the optimum of a particular objective. What Eckart-Young actually buys us is the reassurance that the rank-$r$ ceiling isn’t the bottleneck: there’s a rank-$r$ solution that’s essentially as good as the full update, and we’re trusting gradient descent to find something close to it. The empirical spectra we plotted earlier are what justify that trust for real fine-tuning.

## Wrapping up

That’s LoRA end to end: the linear algebra that says low-rank approximation is a sensible thing to do, the empirical observation that fine-tuning updates are low-rank, a `LoRALinear` layer that adds a trainable rank-$r$ bypass to a frozen weight, the injection code to retrofit it onto an existing model, and the merge trick that makes inference free. A few practical notes I’ve picked up using it at work:

- **Rank and alpha.** Rank $r$ is the obvious knob, but $\alpha$ (the scaling $\tfrac{\alpha}{r}$) matters just as much, it controls how strongly the adapter is applied. A common convention is to set $\alpha = r$ (so the scaling is 1) or $\alpha = 2r$, and then tune the learning rate. Larger $r$ isn’t always better; past the point where it covers the update’s intrinsic rank you’re just adding parameters.
- **Which layers to target.** The original paper ([Hu et al., 2021](#ref-lora)) adapts only the attention $q$ and $v$ projections, which is what we did here. Their ablation found that, at a fixed parameter budget, spreading the adapters across $q$ and $v$ beat putting them all on a single matrix or on $q$ and $k$, the intuition being that $v$ carries the content being mixed while $q$ steers the attention, so adapting both gives the most expressive update per parameter. Adapting the MLP layers as well often helps for harder tasks, at the cost of more parameters.
- **Initialization matters.** Recall we set $A$ with Kaiming init and $B$ to zero, so that $BA = 0$ at the start and the model begins exactly at the pretrained checkpoint. If you initialized both randomly the model would start with a random perturbation bolted on, which throws away the pretrained behavior you’re trying to preserve.
- **Where LoRA falls short.** It’s worth being honest that LoRA isn’t free lunch. When a task genuinely needs a high-rank update, learning a new capability or a large domain shift rather than adapting an existing one, a low-rank adapter can leave performance on the table compared to full fine-tuning. And once you merge an adapter into the weights you lose the ability to cheaply swap or stack adapters at inference, so for multi-adapter serving you keep them unmerged and eat the small forward-pass overhead. Like everything, it’s a tradeoff, just usually a very favorable one.
- **QLoRA.** The natural next step is QLoRA ([Dettmers et al., 2023](#ref-qlora)), which quantizes the frozen base weights to 4-bit while keeping the LoRA adapters in higher precision, pushing the memory savings even further. That’s a good candidate for a future post in this series.

As always, the code is meant to be read top to bottom and run, not taken as production-grade. If you spot a bug, it’s divine benevolence that it ran at all. Next up in the from-scratch series I’ll either tackle QLoRA to push the memory story further, or pick up another byte-sized topic, see you in the next one.

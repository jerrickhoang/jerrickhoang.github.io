I'll assume you don't know much about the VLM literature, but that you're comfortable with decoder-only LLMs.

I've been using Qwen-VL models a lot at work lately, and at some point I realized I had no real idea how the architecture got to where it is. So I sat down and traced the whole lineage, from the very first Qwen-VL to Qwen3.5, and this post is that trace. The Qwen family itself is a series of open-weight large language models from Alibaba's Qwen team, running from the original Qwen-7B (2023) all the way to today's Qwen3 and Qwen3.5, with dense models at various scales and Mixture-of-Experts variants at the larger end. Qwen-VL is the vision-language branch of that family: multimodal models built on top of the corresponding Qwen text backbones, extending them to see images and, from Qwen2-VL onward, video.

What I find interesting is how much changes across the line Qwen-VL → Qwen2-VL → Qwen2.5-VL → Qwen3-VL → Qwen3.5. Each step chips away a little more at the boundary between the vision encoder and the language model. We start with a fixed 256-vector image summary fed into a frozen LLM, and we end with a single early-fusion model trained jointly on text and image tokens from the very first step. Let's walk through it generation by generation.

## Qwen-VL (2023)

Qwen-VL is about 90% the same as OpenCLIP with a few tweaks, so let's dig into OpenCLIP first, then look at what they changed and why.

### OpenCLIP

CLIP (Contrastive Language-Image Pre-training) is the OpenAI method that trains a vision encoder and a text encoder jointly so that matching image-caption pairs land near each other in a shared embedding space, learned over hundreds of millions of web image-text pairs. The resulting vision encoder turns out to be a remarkably strong general-purpose feature extractor, which is why it became the default starting point for vision-language models. OpenCLIP is the open-source reproduction and extension of that work by the LAION community, trained on the public LAION-5B dataset and released as openly downloadable checkpoints, and most VLMs (Qwen-VL included) use these rather than OpenAI's original weights. ViT-bigG refers to the specific size of Vision Transformer architecture used: a roughly 1.9B-parameter ViT, the largest publicly-trained CLIP-style encoder at the time (the size ladder runs B → L → H → g → G, with bigG being the top). Qwen-VL initializes its visual encoder from OpenCLIP's ViT-bigG checkpoint, meaning it inherits a well-aligned, semantically-rich image representation for free and only has to fine-tune it during multimodal training rather than learning vision from scratch.

The overall architecture,

```
Image (224×224×3)
 └─ Conv2d(patch=14, stride=14) → (B, 1664, 16, 16)
 └─ reshape + permute → (B, 256, 1664)        [16×16 = 256 patches]
 └─ prepend CLS token → (B, 257, 1664)
 └─ + positional embedding (257, 1664) learned
 └─ ln_pre → (B, 257, 1664)
 └─ 48 × ResidualAttentionBlock
      ├─ LayerNormFp32 (always fp32, weights stay in compute dtype)
      ├─ MultiHeadAttention 16 heads, head_dim=104
      ├─ LayerNormFp32
      └─ MLP (1664 → ~8193 → 1664, QuickGELU)
 └─ ln_post(x[:, 0]) → (B, 1664)               ← CLS token pooling
 └─ @ proj → (B, 1280)                         ← shared embedding space

Text (77 tokens)
 └─ token + pos embedding → (B, 77, 1280)
 └─ 32 × ResidualAttentionBlock (causal mask)
 └─ ln_final + EOT pooling → (B, 1280)
 └─ @ text_projection → (B, 1280)              ← shared embedding space

Loss: symmetric cross-entropy on (image_feat @ text_feat.T) * exp(logit_scale)
```

#### The Vision Encoder

Dissecting [open_clip's `transformer.py`](https://github.com/mlfoundations/open_clip/blob/main/src/open_clip/transformer.py), we can see that the vision encoder generally consists of the following steps,

#### Step 1: patch embeddings via Conv2d

```python
# ── 1. Patch embedding ──────────────────────────────────────── # Conv2d with kernel=stride=patch_size turns (B,3,H,W) → (B,width,grid,grid) # bias=False: no per-channel offset before the transformer
self.conv1 = nn.Conv2d(3, width, patch_size, stride=patch_size, bias=False)
```

Where, despite the name, `width` is the embedding dimension. It’s the `d_model` of the vision encoder.

#### Step 2: class embeddings and positional encoding

```python
        # class embeddings and positional embeddings
        scale = width ** -0.5
        self.class_embedding = nn.Parameter(scale * torch.randn(width))
        if pos_embed_type == 'learnable':
            self.positional_embedding = nn.Parameter(
                scale * torch.randn(self.grid_size[0] * self.grid_size[1] + 1, width))
        elif pos_embed_type == 'sin_cos_2d':
            # fixed sin-cos embedding
            assert self.grid_size[0] == self.grid_size[1],\
                'currently sin cos 2d pos embedding only supports square input'
            self.positional_embedding = nn.Parameter(
                torch.zeros(self.grid_size[0] * self.grid_size[1] + 1, width), requires_grad=False)
            pos_embed_type = get_2d_sincos_pos_embed(width, self.grid_size[0], cls_token=True)
            self.positional_embedding.data.copy_(torch.from_numpy(pos_embed_type).float())
        else:
            raise ValueError
```

We notice that they scale the learnable class embeddings and positional embeddings by scale of `sqrt(width)` (which is `sqrt(d_model)` as clarified above). The reason is the same as the reason why we do this inside attention layer. Suppose we don’t do this, then the norm of the class embedding vector will be,

$$
\lVert \text{class\_embedding} \rVert = \lVert x \rVert = \mathbb{E}\left[\sqrt{\sum_{j=1}^{d_{\text{model}}} z_j^2}\right] \approx \sqrt{d_{\text{model}}}, \qquad z_j \sim \mathcal{N}(0, 1)
$$

So this grows with `d_model`, which tends to produce a very skewed loss landscape. Say `d_model` is around 1600. Recall the attention dot product at the very end of the model,

$$
\operatorname{score}(q, k) = \frac{q^\top k}{\sqrt{d_{\text{head}}}} = \frac{\lVert q \rVert\lVert k \rVert \cos\theta}{\sqrt{d_{\text{head}}}} \approx \frac{40 \cdot 40 \cos\theta}{10} = 160\cos\theta
$$

Even for a random angle where cos(θ) ≈ 0.1, scores are around ±16. Feed that into softmax:

$$
\operatorname{softmax}\left([16, -16, 0.3, -2.1, \ldots]\right) \approx [1.0, 0.0, 0.0, \ldots]
$$

The softmax is completely saturated at initialization: one token gets all the attention weight and the rest get essentially zero. This means:

- gradients through the attention weights are nearly zero (softmax is flat in its saturated regime)
- the model can't learn meaningful attention patterns early in training
- we get a very difficult loss landscape from step 1

#### Step 3: patch dropout

FLIP (Fast Language-Image Pre-training, [Li et al., 2023](#ref-flip)) is a Meta AI method for training CLIP more efficiently by randomly masking out and removing a large portion of image patches during training. The core claim is that masking lets you learn from more image-text pairs in the same wall-clock time, contrasting more samples per iteration at a similar memory footprint.

The reason this works at all is that natural images are highly redundant, so a model that sees 50% of patches at random still gets enough signal to align with the paired text caption. And since we’re running 2× more samples per unit compute, the net effect is better training efficiency than using all patches every step.

A few things worth noticing:

- Tokens are removed, not zeroed

This is the key difference from regular dropout or MAE-style masking. Regular dropout zeros values in place, so the sequence length stays the same. PatchDropout **physically removes** tokens from the sequence:

```
x = x[batch_indices, patch_indices_keep]  # sequence shrinks
```

So if we drop 50% of 256 patches, the transformer sees a sequence of length 129 (128 patches + CLS), not 257. This matters because attention is O(N²), so dropping 50% of patches gives us roughly 4× cheaper attention per sample during training.

- CLS token is always preserved

```python
cls, x = x[:, :1], x[:, 1:]   # split off CLS
# ... drop patches from x only ...
x = torch.cat([cls, x], dim=1) # reattach CLS
```

This is load-bearing: the CLS token is what gets pooled at the end to produce the image embedding. If it were randomly dropped some fraction of training steps, the model would never reliably learn to use it.

- No train-inference skew

During training with 50% drop rate: sequence length = 129. At inference: sequence length = 257. The model sees a different sequence length between train and eval.

This works cleanly because positional embeddings are **absolute and per-token**: each surviving patch carries its own position embedding encoding where in the image it came from. The transformer doesn't need to know how many other patches exist; it just processes whatever tokens it receives. There's no relative ordering assumption that breaks when tokens disappear.

#### Step 4: the transformer stack

There’s not much difference between the transformer stack here and a transformer stack from a regular LLM except a few small details,

- `LayerNormFp32`: LN always in fp32, regardless of autocast

```python
class LayerNormFp32(nn.LayerNorm):
    def forward(self, x: torch.Tensor):
        orig = x.dtype
        return F.layer_norm(
            x.float(), self.normalized_shape,
            self.weight.float(), self.bias.float(), self.eps
        ).to(orig)
```

A regular transformer under torch.autocast(bf16) would run LN in bf16. OpenCLIP always upcasts to fp32 for the LN computation, then casts back.

**Why it matters:** LN involves computing variance over a sequence, which requires accumulating squared differences. In bf16 (10-bit mantissa), this accumulation is numerically unstable at large widths: you get catastrophic cancellation when `x² - mean(x)²` involves large, nearly-equal numbers. At width 1664 with 257 tokens, this is a real concern. The fp32 upcast is cheap (just the norm, not the whole layer) but critical for training stability. You'll see this pattern in every serious large-scale ViT.

- `QuickGELU`: a sigmoid approximation instead of exact GELU

```python
class QuickGELU(nn.Module):
    def forward(self, x):
        return x * torch.sigmoid(1.702 * x)
```

Exact GELU is x * Φ(x) where Φ is the Gaussian CDF, computed via 0.5 * x * (1 + tanh(√(2/π) * (x + 0.044715 * x³))) or the erf formula. QuickGELU replaces this with a sigmoid approximation.

**Why it matters:** this was baked into the original OpenAI CLIP release, and OpenCLIP preserved it for checkpoint compatibility. If you swap to exact GELU, the pretrained weights behave differently. The two are numerically close but not identical; the sigmoid approximation is slightly faster on some hardware but slightly less accurate. Newer OpenCLIP configs (e.g. trained on DataComp) switch to exact `nn.GELU`, but bigG uses QuickGELU.

- Using `LayerScale` to stabilize deep ViT training (from "Going Deeper with Image Transformers", CaiT, [Touvron et al., 2021](#ref-cait))

```python
class LayerScale(nn.Module):
    def __init__(self, dim, init_values=1e-5, inplace=False):
        self.gamma = nn.Parameter(init_values * torch.ones(dim))
    def forward(self, x):
        return x * self.gamma
```

This is an old technique that's probably not needed these days, though some older models like PaLM and Gemma still used it. It showed up because historically most ViTs used post-norm and kept running into stability issues.

In a standard pre-norm transformer block, the forward pass looks like:

```
x = x + Attention(LN(x))
x = x + MLP(LN(x))
```

The residual connection means every block adds to the stream. After L layers x_L = x_0 + Δ_1 + Δ_2 + ... + Δ_L

where each `Δ_i` is the output of an attention or MLP sublayer. At initialization, each `Δ_i` is a random quantity with some variance σ². Because the deltas are approximately independent at init, the total variance of the residual stream grows as `Var(x_L) ≈ Var(x_0) + L · σ²`

For a shallow network (L=12) this is manageable. For ViT-bigG with L=48 (and each layer contributing both an attention and an MLP delta, so effectively 96 additions), the residual stream norm can grow dramatically, making training unstable. This is why very deep ViTs historically failed to train without special tricks.

With LayerScale,

Instead of `x = x + Attention(LN(x))`, it becomes `x = x + γ * Attention(LN(x))`,

where `γ` is a vector of `dim` learnable scalars initialized to a very small value (e.g. `1e-5`). At the start of training:

$$
\begin{aligned}
\operatorname{Var}(x_L) &\approx \operatorname{Var}(x_0) + L \cdot (10^{-5})^2 \cdot \sigma^2 \\
&\approx \operatorname{Var}(x_0) \qquad \text{(effectively zero contribution from residuals)}
\end{aligned}
$$

The residual stream at initialization is almost entirely the original input x_0 flowing through unchanged. The model starts out as essentially an identity function, and the signal passes through all 48 layers nearly untouched.

The original transformer (Vaswani 2017) used **post-norm** `x = LN(x + Attention(x))`. Post-norm is notoriously hard to train deep because the raw, unscaled residual `Attention(x)` gets added before normalization, which is exactly the explosion problem described above. Most early ViT papers inherited this. Modern LLMs (GPT, LLaMA, etc.) use **pre-norm** `x = x + Attention(LN(x))`. Pre-norm is inherently more stable because the input to every sublayer is normalized before computation. The residual stream still accumulates, but each `Δ_i` is computed from a normalized input, which bounds the magnitude of what gets added. LayerScale was developed partly as a patch for the era when ViTs were still using post-norm or shallow pre-norm wasn't enough.

#### Step 4a: attention pooling

Depending on the variant of OpenCLIP, the pooling mechanism is slightly different. The `coca_ViT-bigG-14` variant (see CoCa, [Yu et al., 2022](#ref-coca)) uses attention pooling. Qwen-VL doesn't inherit from the CoCa variant, it inherits from the plain `ViT-bigG-14` variant, but it still uses a similar pooling approach that's also cross-attention based.

It's essentially a **learned, query-conditioned compression** from `(N, 257, 1664)` down to `(N, 256, 1280)` in a single cross-attention operation.

```python
class AttentionalPooler(nn.Module):
    def __init__(
        self,
        d_model     : int,          # output dim = embed_dim = 1280
        context_dim : int,          # vision encoder width = 1664
        n_head      : int = 8,
        n_queries   : int = 256,
        norm_layer  : Callable = LayerNorm,   # NOTE: LayerNorm, not LayerNormFp32
    ):
        self.query = nn.Parameter(torch.randn(n_queries, d_model))
        self.attn  = nn.MultiheadAttention(
            d_model, n_head,
            kdim=context_dim, vdim=context_dim,   # asymmetric dims
            batch_first=True
        )
        self.ln_q = norm_layer(d_model)        # normalise queries
        self.ln_k = norm_layer(context_dim)    # normalise patch tokens

    def forward(self, x: torch.Tensor):
        N = x.shape[0]
        x   = self.ln_k(x)                                    # (N, 257, 1664)
        q   = self.ln_q(self.query)                            # (n_queries, 1280)
        out = self.attn(
            q.unsqueeze(0).expand(N, -1, -1),                 # (N, n_queries, 1280)
            x, x,                                              # K, V from patches
            need_weights=False
        )[0]
        return out                                             # (N, n_queries, 1280)
```

Cross-attention lets you ask a question of a sequence and get a weighted answer back. The general form is:

```
Q comes from one place   →  "what am I looking for?"
K, V come from another   →  "here's what's available"

output = weighted_sum(V, weights=softmax(Q·Kᵀ))
```

In self-attention, Q, K, and V all come from the same sequence: tokens ask questions of each other. In cross-attention they come from different places, where one set of queries interrogates a separate set of keys and values. The AttentionalPooler uses cross-attention where:

```
Q = learned parameters     (256, 1280)    →  "what to look for"
K = patch tokens           (257, 1664)    →  "available information"
V = patch tokens           (257, 1664)    →  "what to retrieve"
```

Each of the 256 query vectors is a learned question about the image. You can think of them as detectors, each tuned during training to extract a specific type of information from the patch sequence:

```
query[0]  →  might learn to ask "where are edges / textures?"
query[1]  →  might learn to ask "is there a face? where?"
query[42] →  might learn to ask "what's the dominant color region?"
query[99] →  might learn to ask "what's in the background?"
```

Nobody assigns these meanings, they emerge from training. But the point is that each query independently attends to whichever patches are most relevant to its question, via the attention weights:

```
attn_weights[i] = softmax(query[i] · Kᵀ)   # shape: (257,)
output[i]       = sum over patches of attn_weights[i] * V
```

So output[i] is a weighted summary of the patch sequence, weighted by how relevant each patch was to query i's question.

```
Input patches from transformer
(N, 257, 1664)
 │
 ├─ ln_k ──────────────────────────── (N, 257, 1664)  [K, V]
 │
Learned queries
(256, 1280)
 │
 ├─ ln_q ──────────────────────────── (256, 1280)
 ├─ unsqueeze + expand ────────────── (N, 256, 1280)  [Q]
 │
 └─ cross-attention ───────────────────────────────────────┐
       Q (N, 256, 1280) @ W_q → (N, 8, 256, 160)           │
       K (N, 257, 1664) @ W_k → (N, 8, 257, 160)           │
       V (N, 257, 1664) @ W_v → (N, 8, 257, 160)           │
       scores  = Q·Kᵀ          → (N, 8, 256, 257)          │
       weights = softmax(scores)→ (N, 8, 256, 257)          │
       out     = weights·V     → (N, 8, 256, 160)          │
       merged  = reshape       → (N, 256, 1280) @ W_o      │
Output                                                      │
(N, 256, 1280) ◄────────────────────────────────────────────┘
```

The `(N, 8, 256, 257)` score matrix is the heart of it. Read it as: for each batch element, for each attention head, each of the 256 queries has a score against each of the 257 patch tokens. After softmax these become 256 independent probability distributions over the 257 patches, where each query independently decides which patches to read from. Query 0 might put 80% of its weight on the top-left corner patches, query 1 might spread evenly across the whole image. They're fully independent readouts of the same patch sequence.

#### Step 4b: CLS token pooling

Depending on the variant of OpenCLIP, the pooling mechanism is slightly different. The `ViT-bigG-14` variant uses CLS token pooling.

After the transformer you have `(B, 257, 1664)`, one vector per token. The contrastive loss needs a **single vector** to represent the whole image so it can be compared against the text embedding, so we have to compress a sequence down to one vector.

The naive option is mean pooling, where you just average all the patch vectors. But mean pooling is a fixed, non-learnable operation that treats every patch equally regardless of content. A blank sky patch gets the same weight as the patch containing the main subject.

So the question is: can we let the model **learn** how to aggregate?

The trick is to prepend one extra learnable token to the sequence before the transformer runs. This token has no patch content, it's just a free parameter that training can shape into anything. After the transformer, it has attended to all 256 patches across all 48 layers and had its representation updated by them, and we use it as the image summary.

The key insight is that this token becomes a global aggregator **not by design but by training pressure**: it's the only token that the loss gradient flows through directly, so the entire network is forced to route global information into it.

```
patch tokens  →  build rich contextual representations (attending to each other)
                                    ↓
CLS token     →  reads from contextually-enriched patches  →  global summary
```

Pseudocode,

```python
# ── 1. The parameter ──────────────────────────────────────────────
# One learnable vector of size (width,), initialized with width**-0.5
# scaling so its initial norm is O(1).
self.class_embedding = nn.Parameter(scale * torch.randn(width))
#                                                         (1664,)

# ── 2. Prepended in forward, before the transformer ──────────────
# Expand to batch size and prepend to patch sequence.
cls = self.class_embedding \
          .unsqueeze(0).unsqueeze(0) \
          .expand(B, -1, -1)           # (B, 1, 1664)

x = torch.cat([cls, x], dim=1)        # (B, 256, 1664) → (B, 257, 1664)
x = x + self.positional_embedding     # (B, 257, 1664)

# ── 3. Runs through all 48 transformer layers unchanged ──────────
x = self.transformer(x)               # (B, 257, 1664)
# CLS (position 0) and all patches attend to each other freely.
# No special masking: CLS is just one more token.

# ── 4. Pool: take position 0 only ────────────────────────────────
pooled = x[:, 0]                      # (B, 1664)  ← CLS token
# Patch tokens x[:, 1:] are discarded.

# ── 5. Normalize and project into shared embedding space ─────────
pooled = self.ln_post(pooled)         # (B, 1664)
pooled = pooled @ self.proj           # (B, 1280)  ← contrastive embed space
```

Patch tokens have spatial meaning, e.g. position 1 corresponds to the top-left 14×14 pixel region. Using a patch token as the global summary would bake in a spatial bias. CLS sits at position 0 with its own dedicated positional embedding but no spatial content, so training can shape it freely into a pure aggregator without fighting any spatial prior.

### Qwen-VL Tweaks

Source code: [`visual.py` in Qwen-VL-Chat](https://huggingface.co/Qwen/Qwen-VL-Chat/blob/main/visual.py).

As mentioned, Qwen-VL is 90% the same as OpenCLIP, with a few modern tweaks.

#### Difference 1: no CLS token

**OpenCLIP:**

```python
self.class_embedding = nn.Parameter(scale * torch.randn(width))
# prepended in forward:
cls = _expand_token(self.class_embedding, x.shape[0])
x = torch.cat([cls, x], dim=1)   # (N, 257, 1664)
```

Qwen-VL: No class_embedding at all. The forward goes straight from patches to transformer:

```python
x = self.conv1(x)                # (N, width, 32, 32)
x = x.reshape(x.shape[0], x.shape[1], -1).permute(0, 2, 1)  # (N, 1024, width)
x = x + get_abs_pos(self.positional_embedding, x.size(1))
x = self.ln_pre(x)
```

Qwen-VL is a generative model. The LLM decoder needs to cross-attend to visual information while generating text token by token, and a single vector is catastrophically lossy for that. When the LLM is generating "the red car on the left", it needs to look up spatial information from the image, not just a global summary.

So instead of compressing to one vector, Qwen-VL compresses to **256 tokens** that the LLM can selectively read from:

```python
# Resampler output: (B, 256, 4096)
# These 256 tokens get concatenated into the LLM's input sequence
# alongside text tokens, as if they were word tokens
```

The LLM then attends to whichever of the 256 visual tokens are relevant at each generation step. This is fundamentally incompatible with a CLS token approach.

```python
class Resampler(nn.Module):
    """
    A 2D perceiver-resampler network with one cross attention layer by
    (grid_size**2) learnable queries and 2d sincos pos_emb
    Outputs: (grid_size**2, embed_dim)
    """
    def __init__(self, grid_size, embed_dim, num_heads, kv_dim=None, norm_layer=nn.LayerNorm):
        super().__init__()
        self.num_queries = grid_size ** 2     # 256 = 16*16

        # fixed 2D sincos positional embedding, not learnable
        self.pos_embed = nn.Parameter(
            torch.from_numpy(get_2d_sincos_pos_embed(embed_dim, grid_size)).float()
        ).requires_grad_(False)               # (256, embed_dim)

        # learned queries, trunc_normal init
        self.query = nn.Parameter(torch.zeros(self.num_queries, embed_dim))
        trunc_normal_(self.query, std=.02)    # (256, embed_dim)

        # explicit KV projection if dims differ
        if kv_dim is not None and kv_dim != embed_dim:
            self.kv_proj = nn.Linear(kv_dim, embed_dim, bias=False)
        else:
            self.kv_proj = nn.Identity()

        self.attn  = nn.MultiheadAttention(embed_dim, num_heads)  # seq-first
        self.ln_q  = norm_layer(embed_dim)
        self.ln_kv = norm_layer(embed_dim)

    def forward(self, x, attn_mask=None):
        pos_embed = get_abs_pos(self.pos_embed, x.size(1))   # interpolate if needed

        x = self.kv_proj(x)                  # (N, S, kv_dim) → (N, S, embed_dim)
        x = self.ln_kv(x).permute(1, 0, 2)  # (N, S, embed_dim) → (S, N, embed_dim)

        N = x.shape[1]
        q = self.ln_q(self.query)            # (256, embed_dim)

        out = self.attn(
            self._repeat(q, N) + self.pos_embed.unsqueeze(1),  # Q: (256, N, embed_dim)
            x + pos_embed.unsqueeze(1),                         # K: (S, N, embed_dim)
            x,                                                  # V: (S, N, embed_dim)
            attn_mask=attn_mask
        )[0]
        return out.permute(1, 0, 2)          # (256, N, embed_dim) → (N, 256, embed_dim)

    def _repeat(self, query, N: int):
        return query.unsqueeze(1).repeat(1, N, 1)  # (256, embed_dim) → (256, N, embed_dim)
```

```
Input patches from transformer
(N, 1024, 1664)                  ← 32×32 patches at 448px, width=1664
 kv_proj          → (N, 1024, 4096)    project 1664 → 4096
 ln_kv + permute  → (1024, N, 4096)    seq-first for MHA
 query (learned)  → (256, 4096)
 ln_q             → (256, 4096)
 _repeat          → (256, N, 4096)     same queries for all batch elements
 + pos_embed      → (256, N, 4096)     Q gets 16×16 sincos spatial slots
 pos_embed interp → (1024, 4096)       16×16 grid → 32×32 via bicubic
 x + pos_embed    → (1024, N, 4096)    K gets spatial positions
 cross-attention:
   scores  = Q·Kᵀ      → (N, 32, 256, 1024)   each query scores all patches
   weights = softmax   → (N, 32, 256, 1024)   256 distributions over 1024 patches
   out     = weights·V → (N, 32, 256, 128)    each query reads patch content
 merge heads      → (N, 256, 4096)
 permute back     → (N, 256, 4096)     ← 256 visual tokens in LLM space
then in VisionTransformer:
 ln_post          → (N, 256, 4096)
 @ proj (4096,4096)→ (N, 256, 4096)    ← fed into LLM token stream
```

Like the AttentionalPooler in CoCa OpenCLIP, Qwen's Resampler also uses cross-attention with 256 learned queries. The main difference is the positional embedding: a fixed 2D sincos, applied to both Q and K.

```python
self.pos_embed = nn.Parameter(
    torch.from_numpy(get_2d_sincos_pos_embed(embed_dim, grid_size)).float()
).requires_grad_(False)   # (256, 4096)
```

This is a fixed 2D sincos embedding computed once at init and never updated; `requires_grad_(False)` explicitly freezes it. The shape is (256, 4096), one 4096-dim position vector per query slot, arranged as a 16×16 spatial grid.

How `get_2d_sincos_pos_embed` works:

```python
def get_2d_sincos_pos_embed(embed_dim, grid_size):
    # Create a 2D grid of (row, col) coordinates
    grid_h = np.arange(grid_size)   # [0, 1, ..., 15]
    grid_w = np.arange(grid_size)   # [0, 1, ..., 15]
    grid   = np.meshgrid(grid_w, grid_h)   # two (16,16) arrays

    # Encode each axis with sincos at different frequencies
    # half the dims encode row position, half encode col position
    emb_h = get_1d_sincos(embed_dim // 2, grid[0])  # (256, 2048)
    emb_w = get_1d_sincos(embed_dim // 2, grid[1])  # (256, 2048)

    return np.concatenate([emb_h, emb_w], axis=1)   # (256, 4096)
```

The key property: position (row=3, col=7) produces a unique vector, and nearby positions produce similar vectors. This gives the Resampler spatial awareness, so query 0 knows it corresponds to the top-left region of the image and query 255 knows it corresponds to the bottom-right.

Now critically, in the forward pass this pos_embed is added to **Q and K but not V**:

```python
out = self.attn(
    self._repeat(q, N) + self.pos_embed.unsqueeze(1),  # Q gets pos
    x + pos_embed.unsqueeze(1),                         # K gets pos
    x,                                                  # V: no pos
)
```

Why add to Q and K but not V?

- **Q + pos**: each query knows its spatial slot. Query at position (3,7) is "looking for" information that belongs in that spatial region of the output.
- **K + pos**: each patch key knows where it is in the image. Patch at position (12, 20) signals its location.
- **V, no pos**: the values carry pure content. When query (3,7) attends to patch (12,20), what it retrieves should be the semantic content of that patch, not a position-tagged version of it. Position is used to decide whether to attend; it shouldn't contaminate what gets retrieved.

This is the same principle as in rotary position embeddings: position influences attention routing but not the attended values.

### Training Stages

The training process of Qwen-VL ([Bai et al., 2023](#ref-qwenvl)) consists of three stages: two stages of pre-training and a final stage of instruction fine-tuning.

#### Stage 1: pre-training, align the connector

**What's frozen / unfrozen:** The large language model is frozen and only the vision encoder and VL adapter are optimized in this stage.
**Why:** the Resampler is randomly initialized, so it has no idea how to map ViT features into LLM space yet. Training only the connector and ViT first, with the LLM frozen, forces the adapter to learn a stable projection without destabilizing the LLM's pretrained weights.

**Data:** a large-scale, weakly labeled, web-crawled set of image-text pairs. The original dataset contains 5 billion image-text pairs, and after cleaning, 1.4 billion remain, with 77.3% English and 22.7% Chinese.

**Resolution:** 224×224, the same as the ViT-bigG-14 pretraining resolution, so no interpolation is needed yet.

**Training objective:** cross-entropy loss on text tokens. The model sees an image and has to predict the paired caption, so the visual features have to be informative enough that the frozen LLM can generate the text from them.

**Key hyperparameters:** AdamW optimizer with β₁=0.9, β₂=0.98, eps=1e-6. Cosine learning rate schedule with maximum lr=2e-4 and minimum lr=1e-6, linear warmup of 500 steps. Weight decay=5e-2, gradient clipping=1.0. Layer-wise learning rate decay for the ViT with a decay factor of 0.95. Batch size of 30,720. The entire first stage lasts 50,000 steps, consuming roughly 1.5 billion image-text samples.

The layer-wise LR decay on the ViT (0.95 per layer from the top down) is worth noting: earlier layers get a much smaller LR than later layers, which preserves the low-level features learned during CLIP pretraining while letting the higher-level representations adapt.

#### Stage 2: multi-task pre-training, unlock everything and bump resolution

**What's frozen / unfrozen:** the large language model is unlocked and the whole model is trained.

This is the most significant stage: the LLM now participates in training, learning to interpret visual tokens from the adapter.

**Resolution bump:** the input resolution of the visual encoder goes from 224×224 to 448×448, reducing the information loss from image down-sampling.

This is why the Resampler has the bicubic positional interpolation. Going from 16×16 patches (224px) to 32×32 patches (448px) means the patch count goes from 256 to 1024, so the Resampler still outputs 256 tokens but now compresses from 1024 patches instead of 256.

**Data, 7 tasks at once:**

| **Task** | **Samples** | **Datasets** |
| --- | --- | --- |
| Captioning | 19.7M | LAION-en/zh, DataComp, Coyo, CC12M/3M, SBU, COCO |
| VQA | 3.6M | GQA, VGQA, VQAv2, DVQA, OCR-VQA, DocVQA |
| Grounding | 3.5M | GRIT |
| Ref Grounding | 8.7M | GRIT, Visual Genome, RefCOCO/+/g |
| Grounded Captioning | 8.7M | GRIT, Visual Genome, RefCOCO/+/g |
| OCR | 24.8M | SynthDoG-en/zh, Common Crawl pdf/HTML |
| Text Generation | 7.8M | In-house |


The grounding and OCR tasks are what make Qwen-VL distinctive, since most VLMs at the time only trained on captioning and VQA. Training on bounding box prediction forces the model to produce spatially precise outputs, which is exactly why the 2D sincos positional embeddings in the Resampler matter: the model needs to know where each visual token came from spatially.

For text generation, an in-house corpus is used to keep the LLM's language ability intact. This prevents catastrophic forgetting: without pure text data, the LLM would gradually lose its language capabilities as it adapts to multimodal inputs.

**Training:** trained for 19,000 steps with 400 warmup steps and a cosine learning rate schedule.

#### Stage 3: supervised fine-tuning into Qwen-VL-Chat

**What's frozen / unfrozen:** the visual encoder is frozen and the language model and adapter module are optimized.

Interestingly, the freeze pattern flips from Stage 1: now the ViT is frozen (its representations are considered stable and good) and the LLM and adapter are tuned for instruction following.

**Data:** the instruction tuning data amounts to 350k samples. Most of it comes from caption data or dialogue data generated through LLM self-instruction. An additional set of dialogue data is built through manual annotation, model generation, and strategy concatenation to bring in localization and multi-image comprehension abilities.

**Format:** the instruction tuning dataset uses the ChatML format, where each interaction's statement is marked with two special tokens `<|im_start|>` and `<|im_end|>` to make dialogue termination easy. During training, only answers and special tokens are supervised, not role names or question prompts.

**Hyperparameters:** global batch size of 128, maximum learning rate of 1e-6, minimum learning rate of 1e-6, and a linear warmup of 3,000 steps.

The very low LR (1e-6) reflects that this stage is fine adjustment: the model already has strong visual understanding from Stage 2, so this stage is purely about formatting and instruction-following behavior.

The freeze pattern across stages,

```
           Stage 1          Stage 2          Stage 3
ViT        ✅ trained       ✅ trained       ❌ frozen
Resampler  ✅ trained       ✅ trained       ✅ trained
LLM        ❌ frozen        ✅ trained       ✅ trained
```

The logic is deliberate:

**Stage 1:** teach the connector to speak ViT's language without disturbing the LLM. The LLM is a fixed target, and the connector has to adapt to it.

**Stage 2:** once the connector produces reasonable visual tokens, unlock the LLM so the whole system can jointly optimize for diverse tasks at higher resolution.

**Stage 3:** the visual representations are now stable and high quality, so we freeze the ViT to prevent drift and focus the remaining parameters on dialogue behavior.

## Qwen2-VL (2024)

Qwen2-VL makes three big changes compared to the original Qwen-VL,

- A big focus on dynamic resolution (handling media at different resolutions)
- A big focus on multimodal handling (both images and videos)
- A better base model (ViT-G is replaced with DFN-ViT)

### DFN-ViT

For Qwen2-VL, they decided not to initialize the vision encoder from OpenCLIP's ViT-G and used Apple's DFN ViT instead, which comes from the Data Filtering Networks paper (DFN, [Fang et al., 2023](#ref-dfn)).

#### The problem

Web-scale dataset construction for CLIP usually has two phases: scrape a massive uncurated pool, then filter it down. The filtering step has historically been done with naive heuristics, most commonly "CLIP filtering," where you use an existing CLIP model (usually OpenAI's ViT-B/32) to score image-text cosine similarity and discard low-scoring pairs. The paper asks: **can we learn a better filter, and what makes a good one?**

#### Finding 1: filtering quality ≠ downstream task performance

This is the paper's most surprising and important result. There's no correlation between a model's ImageNet accuracy and its quality as a data filter. A model with 30% lower ImageNet accuracy than OpenAI's ViT-B/32 can be an equally good or better filter, so you can't just substitute a better CLIP model into the filtering pipeline and expect better datasets.

#### Finding 2: the data quality of the filter's training set is everything

What does predict good filtering is the quality of the data used to train the filtering network. Even a small contamination of low-quality data into the filter's training set destroys filtering performance immediately, even though the filter's own ImageNet accuracy degrades only gradually. The recipe is simple: train a small CLIP model on a small but high-quality dataset, and use that as your filter.

#### The DFN pipeline

The full pipeline is three steps:

1. Start with a small high-quality dataset (they use HQITP-350M, 357M human-verified image-text pairs, initialized from OpenAI's ViT-B/32 checkpoint)
2. Fine-tune this CLIP model on MS-COCO + Flickr30k + ImageNet with text templates; this is the DFN
3. Apply the DFN to filter CommonPool-12.8B (keeping the top 15% by cosine similarity) to produce DFN-2B, or apply it to a 43B pool to produce DFN-5B

Standard ML tricks for improving models also improve DFNs: data augmentation, larger batch sizes, more training steps, and weight ensembling to reduce overfitting from fine-tuning.

Overall, DFN-ViT is just a smaller version of OpenCLIP ViT-G, trained on a much better dataset.

|  | **ViT-bigG-14 (Qwen-VL)** | **DFN ViT-H-14 (Qwen2-VL)** |
| --- | --- | --- |
| Width | 1664 | 1280 |
| Layers | 48 | 32 |
| Heads | 16 (1664/104) | 16 (1280/80) |
| Head dim | 104 | 80 |
| MLP ratio | 4.9231 | 4.0 (standard) |
| Patch size | 14 | 14 |
| Embed dim | 1280 | 1024 |
| QuickGELU | ✅ (checkpoint) | ✅ (explicit in config) |
| Params (vision) | ~1.9B | ~675M |
| Training data | LAION-2B (~2B pairs) | DFN-5B (filtered from 43B) |

### Dynamic Resolution

One big push for Qwen2-VL is supporting dynamic resolution. This drives a few changes,

#### Change 1: the Resampler is gone, replaced by a simple MLP

The Resampler compressed to a **fixed** 256 tokens regardless of input resolution: a 100×100 image got 256 tokens, and so did a 2000×2000 image. That's wasteful in one direction and lossy in the other. They replaced the Resampler with a simple vision merger. It's the same operation as **patch merging in Swin Transformer**. After the ViT produces patch tokens arranged in a spatial grid, you take every 2×2 block of neighboring tokens and concatenate their feature vectors, then project down with a linear layer:

```python
class VisionMerger(nn.Module):
    """
    Merges 2×2 spatial blocks of patch tokens into one token.
    Equivalent to Swin Transformer's PatchMerging.
    """
    def __init__(self, input_dim: int, output_dim: int):
        super().__init__()
        # 4 neighbors concatenated → project to LLM hidden size
        self.proj = nn.Linear(input_dim * 4, output_dim)

    def forward(self, x: torch.Tensor, grid_h: int, grid_w: int):
        # x: (N, grid_h * grid_w, input_dim)
        N, _, C = x.shape
        x = x.reshape(N, grid_h, grid_w, C)

        # gather 2×2 spatial neighbors and concatenate along feature dim
        x = torch.cat([
            x[:, 0::2, 0::2, :],   # top-left
            x[:, 0::2, 1::2, :],   # top-right
            x[:, 1::2, 0::2, :],   # bottom-left
            x[:, 1::2, 1::2, :],   # bottom-right
        ], dim=-1)                  # (N, grid_h//2, grid_w//2, 4*C)

        x = x.reshape(N, -1, 4 * C)   # (N, grid_h//2 * grid_w//2, 4*C)
        return self.proj(x)            # (N, grid_h//2 * grid_w//2, output_dim)
```

The output dimension of `proj` is the **LLM's hidden size directly**, so the merger compresses spatially and projects into LLM space in a single linear layer. The Resampler needed a whole `kv_proj` + cross-attention + `ln_post` + `proj` chain to do this; here it's one matrix multiply.

They also added two special tokens, `<|vision_start|>` and `<|vision_end|>`, that act as hard boundaries in the LLM's attention. The LLM learns during training that tokens between these markers are visual, so it can develop different attention patterns for visual versus text tokens without any architectural changes like gated cross-attention. This is simpler than Flamingo's interleaved cross-attention layers and keeps the LLM architecture completely standard.

Shape traces:

```
224×224 input:
  ViT patches:  16×16 = 256 tokens, each (1280,)
  After merger: 8×8  = 64 tokens,  each (LLM_dim,)   [4×1280 → LLM_dim]
  + special:    64 + 2 = 66 tokens in LLM stream

448×448 input:
  ViT patches:  32×32 = 1024 tokens
  After merger: 16×16 = 256 tokens
  + special:    256 + 2 = 258 tokens

896×896 input:
  ViT patches:  64×64 = 4096 tokens
  After merger: 32×32 = 1024 tokens
  + special:    1024 + 2 = 1026 tokens
```

One thing to note is that they made an intentional tradeoff here between content-blind and content-aware compression,

**Resampler** (content-aware): each output token is an attention-weighted sum over all 1024 patches. A query focused on detecting text might put 80% of its weight on 10 specific patches and ignore the rest. It's selective and adaptive per query.

**MLP merger** (content-blind): each output token is a deterministic concatenation of exactly 4 spatially adjacent patches. Every 2×2 block is treated equally regardless of whether it contains important content or empty background.

```
Resampler:  query[i] → attends to any/all of 1024 patches → soft weighted sum
MLP merger: block[i] → exactly patches (2i_row, 2i_col), (2i_row, 2i_col+1),
                                       (2i_row+1, 2i_col), (2i_row+1, 2i_col+1)
            no flexibility, no content-dependence
```

This seems like a regression, but it's actually fine for two reasons:

First, by the time patches reach the merger they've already been processed by **32 transformer layers of full self-attention**. Each patch token isn't just a representation of its 14×14 pixel region; it has attended to all the other patches across all 32 layers and encodes global context. The merger is compressing already-rich representations, not raw pixel statistics.

Second, the LLM itself can compensate. With 256 visual tokens at 448px, the LLM's self-attention can route information between visual tokens in its own layers. The Resampler's content-aware pooling was only necessary when the LLM received 256 fixed tokens regardless of image size: if you had a 2000×2000 image compressed to 256 tokens by a fixed-query mechanism, a lot of detail was simply gone. With dynamic resolution the LLM gets more tokens for more complex images and can work with them directly.

#### Change 2: 2D RoPE for position encoding

In Qwen-VL's ViT (inherited from OpenCLIP ViT-bigG-14), positional information is encoded as a lookup table:

```python
self.positional_embedding = nn.Parameter(torch.zeros(256, width))
# one learned vector per spatial slot: a fixed 16×16 grid
```

Every patch slot has its own learned vector trained to mean "I am at position (row, col)". The model learns during training that position vector 37 means "upper-right quadrant" and uses this to understand spatial relationships.

The problem: **this table has a fixed number of entries.** If you train at 224px (16×16=256 patches), you have 256 position vectors. If you run at 448px (32×32=1024 patches), you have 1024 patch positions but only 256 trained vectors. The Qwen-VL Resampler patched this by bicubic-interpolating the 16×16 grid to 32×32, but that's distribution shift. The model was never trained on those interpolated position values. It works tolerably, but it's fundamentally a workaround, not a solution.

More importantly, even with interpolation the ViT's internal representations were still shaped by a training regime at fixed resolution. The model's attention patterns learned what "nearby" and "far away" meant in terms of a 16×16 grid. At 32×32, those patterns are applied in a different spatial context than they were trained on.

Standard 1D RoPE (used in LLMs like LLaMA) doesn't use a lookup table at all. Instead it computes positional information **on the fly** by rotating Q and K vectors based on position indices, using sinusoidal functions:

```python
# For position p, dimension pair index d:
theta_d = 1.0 / (base ** (2*d / dim))   # fixed frequency for dim d

# Rotate Q vector at position p:
q_rotated[2d]   = q[2d]   * cos(p * theta_d) - q[2d+1] * sin(p * theta_d)
q_rotated[2d+1] = q[2d]   * sin(p * theta_d) + q[2d+1] * cos(p * theta_d)
```

The critical property of this rotation: when you compute the dot product q_p · k_r between a query at position p and a key at position r, the result only depends on (p - r), the relative position, not on p or r in isolation. This falls out of the rotation algebra:

$$
q_p \cdot k_r = f(\text{content}_q, \text{content}_k, p-r)
$$

This is why LLMs trained with RoPE at context length 4096 can often be extended to 8192 or longer: the model never saw positions beyond 4096 in training, but the relative distances between tokens are the same regardless of absolute position. The position encoding extrapolates by construction.

For a 2D image grid, you extend this by assigning each patch a **(row_id, col_id)** pair and encoding both axes independently using separate halves of the head dimension:

```python
def apply_2d_rope(q, k, grid_h, grid_w, head_dim, base=10000):
    """
    q, k: (N, num_heads, seq_len, head_dim)
    Each token at position (row, col) gets:
      - first half of head_dim rotated by row_id
      - second half of head_dim rotated by col_id
    """
    half = head_dim // 2

    # frequencies for each dimension index
    freqs = 1.0 / (base ** (torch.arange(0, half, 2) / half))  # (half//2,)

    # position indices for row and column axes
    rows = torch.arange(grid_h)   # [0, 1, ..., grid_h-1]
    cols = torch.arange(grid_w)   # [0, 1, ..., grid_w-1]

    # outer product: each position × each frequency
    emb_rows = torch.outer(rows, freqs)  # (grid_h, half//2)
    emb_cols = torch.outer(cols, freqs)  # (grid_w, half//2)

    # tile to match 2D grid: each patch at (r,c) gets row freq r and col freq c
    emb_rows = emb_rows.repeat_interleave(grid_w, dim=0)  # (grid_h*grid_w, half//2)
    emb_cols = emb_cols.repeat(grid_h, 1)                 # (grid_h*grid_w, half//2)

    # build cos/sin for both axes
    cos_row = torch.cat([emb_rows.cos(), emb_rows.cos()], dim=-1)  # (seq, half)
    sin_row = torch.cat([emb_rows.sin(), emb_rows.sin()], dim=-1)
    cos_col = torch.cat([emb_cols.cos(), emb_cols.cos()], dim=-1)
    sin_col = torch.cat([emb_cols.sin(), emb_cols.sin()], dim=-1)

    # apply to first half (row encoding) and second half (col encoding)
    q[..., :half]  = rotate_half(q[..., :half],  cos_row, sin_row)
    q[..., half:]  = rotate_half(q[..., half:],  cos_col, sin_col)
    k[..., :half]  = rotate_half(k[..., :half],  cos_row, sin_row)
    k[..., half:]  = rotate_half(k[..., half:],  cos_col, sin_col)
    return q, k
```

For a patch at (row=3, col=7):

- Dimensions 0 to head_dim//2-1 encode "I am in row 3"
- Dimensions head_dim//2 to head_dim-1 encode "I am in column 7"

The dot product between two patches now encodes both row-distance and column-distance:

```
attn(patch_A at (3,7), patch_B at (5,2))
  = f(content, Δrow=2, Δcol=5)
```

The model learns that attention should decay with both row-distance and column-distance simultaneously, which is exactly the right inductive bias for 2D spatial structure.

#### Change 3: sequence packing at inference

With variable-resolution images in a batch, padding would be extremely wasteful: a 64-token image paired with a 1026-token image in the same batch wastes about 940 pad tokens. Qwen2-VL uses **sequence packing** instead:

```
Without packing (padded batch):
  Image A: [66 tokens][960 PAD tokens]  = 1026 total
  Image B: [1026 tokens]                = 1026 total
  Total compute: 2 × 1026² attention ops

With packing:
  Combined: [66 tokens | 1026 tokens]   = 1092 total
  Attention mask: block-diagonal        (A's tokens never attend to B's)
  Total compute: 66² + 1026² attention ops  ← much cheaper
```

The attention mask is block-diagonal: within each image, tokens attend to each other freely, and across images, attention is masked to zero. This way a single forward pass handles multiple images of completely different sizes without any padding waste.

The paper notes the packed sequence length is capped to control GPU memory: if an image would produce too many patches (e.g. a 4K image at 73×73=5329 patches → 1332 merged tokens), the image is downsampled to stay within the budget.

### Multimodal Handling

#### Change 1: Multimodal Rotary Positional Encoding (M-RoPE)

To support multimodality, the positional encoding of the LLM also needs to change.

After the MLP merger outputs 256 visual tokens, they enter the LLM's token stream. Without M-RoPE, the LLM would assign **sequential 1D positions** to those tokens:

```
text: "describe the image"   →  pos 0, 1, 2, 3
<|vision_start|>             →  pos 4
visual token (row=0, col=0)  →  pos 5
visual token (row=0, col=1)  →  pos 6
visual token (row=0, col=2)  →  pos 7
...
visual token (row=0, col=15) →  pos 20
visual token (row=1, col=0)  →  pos 21    ← same pos distance from (0,15) as (0,14) to (0,15)
visual token (row=1, col=1)  →  pos 22
...
visual token (row=15,col=15) →  pos 260
<|vision_end|>               →  pos 261
"What is on the left?"       →  pos 262, ...
```

With sequential 1D positions, the LLM's attention mechanism knows token 21 is "one step after" token 20, but it has no idea that token 21 is directly below token 5; they're 16 positions apart in the sequence. The LLM would have to learn from content that visual tokens are arranged in a grid, rather than having it encoded directly in the positional structure. This makes spatial reasoning harder and less sample-efficient.

M-RoPE directly encodes the 2D structure into the LLM's Q·K dot products, so the LLM natively "knows" which visual tokens are adjacent, above, below, or far away.

Standard 1D RoPE applies rotations using a single position index `n` to all head dimensions. M-RoPE splits the head dimension into **three equal parts** and applies a different position index to each part:

```python
def apply_mrope(q, k, t_ids, h_ids, w_ids, head_dim, base=10000):
    """
    q, k: (batch, heads, seq_len, head_dim)
    t_ids, h_ids, w_ids: (seq_len,), three position indices per token
    head_dim is split into thirds: [0:D/3] temporal, [D/3:2D/3] height, [2D/3:D] width
    """
    D = head_dim
    third = D // 3

    # compute RoPE frequencies for each dimension index
    freqs = 1.0 / (base ** (torch.arange(0, third, 2).float() / third))

    # build cos/sin for each axis from its position IDs
    cos_t, sin_t = get_rope_cos_sin(t_ids, freqs)  # (seq, third)
    cos_h, sin_h = get_rope_cos_sin(h_ids, freqs)
    cos_w, sin_w = get_rope_cos_sin(w_ids, freqs)

    # apply to respective thirds of Q and K
    q[..., :third]        = rotate(q[..., :third],        cos_t, sin_t)
    q[..., third:2*third] = rotate(q[..., third:2*third], cos_h, sin_h)
    q[..., 2*third:]      = rotate(q[..., 2*third:],      cos_w, sin_w)

    k[..., :third]        = rotate(k[..., :third],        cos_t, sin_t)
    k[..., third:2*third] = rotate(k[..., third:2*third], cos_h, sin_h)
    k[..., 2*third:]      = rotate(k[..., 2*third:],      cos_w, sin_w)

    return q, k
```

The dot product between a query at (t_q, h_q, w_q) and a key at (t_k, h_k, w_k) then decomposes as:

$$
q \cdot k = f_{\text{temporal}}(t_q - t_k) + f_{\text{height}}(h_q - h_k) + f_{\text{width}}(w_q - w_k)
$$

Each axis contributes its own relative position signal independently. Two visual tokens in the same frame (t_q = t_k → Δt=0) but different rows get a large height penalty but zero temporal penalty. Two tokens in different frames at the same spatial position (Δt>0, Δh=0, Δw=0) get a temporal penalty but no spatial penalty. The model can distinguish all these cases cleanly.

For a concrete example: a sequence with text, then an image, then more text:

```
"A photo of"           →  (t=0, h=0, w=0)  (t=1, h=1, w=1)  (t=2, h=2, w=2)
<|vision_start|>       →  (t=3, h=3, w=3)   ← treated like text
visual (row=0, col=0)  →  (t=4, h=4,  w=4 )   ← t constant within image
visual (row=0, col=1)  →  (t=4, h=4,  w=5 )
visual (row=0, col=2)  →  (t=4, h=4,  w=6 )
...
visual (row=1, col=0)  →  (t=4, h=5,  w=4 )   ← h increments with row
visual (row=1, col=1)  →  (t=4, h=5,  w=5 )
...
visual (row=15, col=15)→  (t=4, h=19, w=19)   ← max position = 4 + 15 = 19
<|vision_end|>         →  (t=20, h=20, w=20)  ← max(t,h,w) + 1 = 20
"What is on the left?" →  (t=20,h=20,w=20)  (t=21,...) ...
```

Two things to notice:

**The temporal ID is constant within an image** (`t=4` for all visual tokens). So from the temporal axis's perspective, all visual tokens look like they have the same "time": the LLM's temporal component treats the entire image as a single moment, and only the height and width components carry spatial information.

**Position IDs are much smaller than with 1D sequential assignment.** With 1D RoPE and 256 visual tokens, the last visual token would have position 4+255=259. With M-RoPE, the max position ID is only 4+15=19 (grid size 16, so max row/col is 15). This matters because RoPE generalizes better to position IDs it has seen during training, so smaller max IDs mean better extrapolation to longer sequences at inference.

For video (treated as a sequence of frames), temporal ID increments per frame:

```
Frame 0, patch (row=0, col=0):  (t=0, h=0, w=0)
Frame 0, patch (row=0, col=1):  (t=0, h=0, w=1)
Frame 0, patch (row=1, col=0):  (t=0, h=1, w=0)
...
Frame 1, patch (row=0, col=0):  (t=1, h=0, w=0)   ← same spatial pos, next frame
Frame 1, patch (row=0, col=1):  (t=1, h=0, w=1)
...
Frame 2, patch (row=0, col=0):  (t=2, h=0, w=0)
```

Now (t=0, h=3, w=7) and (t=1, h=3, w=7) are the same spatial location in consecutive frames. Their dot product in the LLM's attention is:

$$
f_{\text{temporal}}(\Delta t = 1) + f_{\text{height}}(\Delta h = 0) + f_{\text{width}}(\Delta w = 0)
$$

The model directly learns to track the same spatial location across time: the dot product stays close to the "same spatial location, nearby time" value regardless of where in the video these frames sit. This is exactly the inductive bias needed for temporal correspondence tasks like object tracking, motion understanding, or noticing what changed between frames.

For a text token at position `n`, the assignment is `(t=n, h=n, w=n)`. The dot product between two text tokens at positions `n` and `m`:

$$
\begin{aligned}
q \cdot k &= f_{\text{temporal}}(n-m) + f_{\text{height}}(n-m) + f_{\text{width}}(n-m) \\
&= 3 \cdot f(n-m) \qquad \text{(since all three components encode the same delta)}
\end{aligned}
$$

This is proportional to the standard 1D RoPE value: the relative position signal is the same, just scaled by 3 because the three head-dimension thirds all encode the same axis. During training, the model's weight matrices absorb this scaling, so functionally, text tokens behave exactly as they would with standard 1D RoPE.

#### Change 2: unified image and video with 3D convolutions

The 3D conv is not a separate video processing module added after the ViT. It **replaces** `self.conv1`, the patch embedding layer itself. This is the key architectural decision.

Standard ViT patch embedding for images:

```python
# 2D conv: processes one frame at a time
self.conv1 = nn.Conv2d(
    in_channels=3,
    out_channels=width,
    kernel_size=patch_size,       # (14, 14)
    stride=patch_size,
    bias=False
)
# (B, 3, H, W) → (B, width, H/14, W/14)
```

Qwen2-VL's patch embedding for video:

```python
# 3D conv: processes pairs of frames together
self.conv1 = nn.Conv3d(
    in_channels=3,
    out_channels=width,
    kernel_size=(2, patch_size, patch_size),   # depth=2 temporal, 14×14 spatial
    stride=(2, patch_size, patch_size),         # stride 2 temporally halves frame count
    bias=False
)
# (B, 3, T, H, W) → (B, width, T/2, H/14, W/14)
```

The weight tensor changes from (width, 3, 14, 14) to (width, 3, 2, 14, 14): it now sees a spatiotemporal volume of 3 × 2 × 14 × 14 = 1176 values per output feature instead of 3 × 14 × 14 = 588. The extra dimension looks at two consecutive frames simultaneously, encoding what changed between them directly into each patch token.

For a video, each output patch token at position `(t, row, col)` is a linear combination of:

- All 3 color channels
- 2 consecutive temporal frames `f=2t` and `f=2t+1`
- A 14×14 spatial neighborhood at `(row, col)`

$$
\operatorname{output\_token}_{t, r, c} = \sum_{c',\Delta t,\Delta h,\Delta w} W_{c',\Delta t,\Delta h,\Delta w}\,\operatorname{input}_{c',\,2t+\Delta t,\,14r+\Delta h,\,14c+\Delta w}
$$

Where dt ∈ {0,1} (the two frames), dh,dw ∈ {0,...,13} (spatial extent).

This means each token isn't a representation of a static 14×14 patch, it's a representation of a **14×14×2 spatiotemporal tube**. The learned weights can encode:

- Static appearance (both frames similar → weight sum encodes content)
- Motion (frames differ → weight difference encodes optical flow-like signal)
- Temporal edge detection (respond strongly to transitions)

All of this is learned end-to-end, so the model discovers whatever temporal features are most useful for the downstream task.

#### Why depth=2 specifically

Depth 2 with stride 2 is the minimal meaningful temporal convolution: it looks at exactly adjacent frame pairs and halves the sequence length. Consider the alternatives:

**Depth 1 (2D conv per frame):** Each patch sees only one frame. No temporal information at the patch level. Motion must be inferred by the transformer from positional IDs alone.

**Depth 2, stride 2 (Qwen2-VL's choice):** Each patch sees exactly 2 adjacent frames. Frame count halved. Minimal local temporal context baked in at embedding time.

**Depth 3+ (deeper temporal conv):** Each patch sees 3+ frames. More temporal context but harder to train, more parameters, and frame count reduction is larger (every 3 frames become 1 token), potentially losing temporal resolution.

Depth 2 is the sweet spot: one step of temporal compression, minimal extra parameters (one extra frame's worth of weights), and it natively handles the 2 FPS sampling rate chosen for Qwen2-VL. At 2 FPS, two adjacent frames are 0.5 seconds apart, which is a natural short-term motion window.

### Qwen2.5-VL Tweaks

Qwen2.5-VL applies several tweaks on top of Qwen2-VL,

#### Change 1: the ViT is redesigned and trained from scratch

**Qwen2-VL:** initialized from DFN ViT-H-14 pretrained weights, then surgically replaced absolute pos embed with 2D-RoPE. The rest of the architecture (GELU, LayerNorm, standard MLP ratio 4.0) was inherited from DFN.

**Qwen2.5-VL:** the vision encoder employs a redesigned Vision Transformer architecture, incorporating 2D-RoPE and window attention to support native input resolutions. The ViT is trained from scratch, with training consisting of CLIP pre-training, vision-language alignment, and end-to-end fine-tuning.

Training from scratch matters because the DFN ViT was never designed with window attention or SwiGLU. Retrofitting those onto a pretrained checkpoint (as Qwen2-VL did with 2D-RoPE) introduces distribution shift. Starting from scratch means the full architecture is co-trained consistently from day one.

The config from the paper confirms the ViT dimensions are identical to Qwen2-VL's:

```
Hidden size:       1280   (same)
Num layers:        32     (same)
Num heads:         16     (same)
Patch size:        14     (same)
```

But two architectural components change:

#### Change 2: SwiGLU replaces GELU, RMSNorm replaces LayerNorm

From the code, the ViT MLP is now:

```python
class Qwen2_5_VLMLP(nn.Module):
    def __init__(self, config, bias: bool = False):
        self.gate_proj = nn.Linear(hidden_size, intermediate_size, bias=bias)
        self.up_proj   = nn.Linear(hidden_size, intermediate_size, bias=bias)
        self.down_proj = nn.Linear(intermediate_size, hidden_size, bias=bias)
        self.act_fn    = ACT2FN[config.hidden_act]   # silu

    def forward(self, hidden_state):
        return self.down_proj(
            self.act_fn(self.gate_proj(hidden_state)) * self.up_proj(hidden_state)
        )
```

This is SwiGLU, the same MLP design used in LLaMA, Qwen2, and most modern LLMs. A standard GELU MLP has one projection hidden → intermediate → hidden. SwiGLU has two parallel projections: one gated (through SiLU activation) and one ungated, multiplied elementwise before the output projection.

The intermediate size also changes: from 5120 (ratio 4.0 in DFN) to **3456** (ratio ~2.7). SwiGLU MLPs typically use a smaller ratio (~8/3 ≈ 2.67) to keep parameter count comparable to standard 4.0-ratio GELU MLPs, since SwiGLU requires two input projections instead of one.

```
Qwen2-VL ViT MLP:      1280 → 5120 → 1280    (1 projection, GELU)    params: 2 × 1280 × 5120 = 13.1M
Qwen2.5-VL ViT MLP:    1280 → 3456 → 1280    (2 projections, SwiGLU) params: 3 × 1280 × 3456 = 13.3M
```

Parameter count is roughly matched while SwiGLU provides richer gating.

RMSNorm replaces LayerNorm throughout the ViT:

```python
class Qwen2RMSNorm(nn.Module):
    def forward(self, hidden_states):
        variance = hidden_states.pow(2).mean(-1, keepdim=True)
        hidden_states = hidden_states * torch.rsqrt(variance + self.variance_epsilon)
        return self.weight * hidden_states
```

RMSNorm drops the mean-centering step of LayerNorm: it only normalizes by the RMS, not by (x - mean) / std. This is cheaper (no mean computation) and was found to work equally well in practice. The explicit motivation in the paper is to align the ViT architecture more closely with the design principles of large language models, specifically adopting RMSNorm for normalization and SwiGLU as the activation. The ViT now shares the same MLP and normalization design as the Qwen2.5 LLM it's paired with, which is a deliberate homogenization of the two components.

#### Change 3: window attention

With fixed 224×224 input, the ViT always has 256 patch tokens. Full self-attention costs O(256²) = 65,536 operations per layer, which is constant and manageable.

With dynamic resolution, a high-res document at 1120×1120 gives 80×80 = 6,400 patches. Full self-attention now costs O(6400²) = 40,960,000 operations per layer, which is **625× more expensive**. This is the direct consequence of dynamic resolution: you removed the fixed-resolution constraint, but full attention's quadratic complexity means high-res images become prohibitively expensive.

Instead of every patch attending to every other patch globally, each patch only attends to patches within a **local spatial window**:

In the Qwen2.5-VL architecture, only four layers employ full self-attention, while the remaining layers utilize windowed attention with a maximum window size of 112×112 pixels (corresponding to 8×8 patches). Regions smaller than 112×112 are processed without padding, preserving their original resolution.

So for a 32-layer ViT:

```
Layers 0–6, 8–14, 16–22, 24–30:  window attention  (28 layers)
Layers 7, 15, 23, 31:             full attention     (4 layers)
```

The cost per window-attention layer:

```
window_size = 8×8 = 64 patches per window
cost = num_windows × window_size² = (N/64) × 64² = 64N   →  O(N), not O(N²)
```

For the 6,400-patch high-res image: 6,400 × 64 = 409,600 versus 40,960,000 for full attention, so it's about 100× cheaper per windowed layer.

Window attention has a structural limitation: patches in one window can't directly attend to patches in a distant window. A patch in the top-left corner of the image has no direct path to a patch in the bottom-right corner unless information propagates through many intermediate windows across layers.

The 4 full-attention layers at positions {7, 15, 23, 31}, placed evenly throughout the 32-layer stack, act as **global communication checkpoints**. Information gathered locally in windows gets globally exchanged at these layers, then local refinement continues in the next window-attention block.

```
Layers 0–6:   local feature extraction (windows)
Layer 7:      global information exchange (full attention)
Layers 8–14:  local refinement with global context (windows)
Layer 15:     global exchange again
Layers 16–22: local refinement
Layer 23:     global exchange
Layers 24–30: local refinement
Layer 31:     final global exchange
```

This is the same design principle as Swin Transformer's shifted window attention, except here the alternation is between full and windowed attention rather than between regular and shifted windows.

There are also a few smaller changes: a two-layer MLP merger instead of one, M-RoPE aligned to absolute time, an LLM backbone upgrade, and more pre-training scale.

## Qwen3-VL (2025)

### SigLIP-2

#### Part 1: the CLIP loss vs the SigLIP loss

**CLIP (OpenCLIP): softmax contrastive loss**

Given a batch of N image-text pairs, CLIP computes an N×N similarity matrix and applies symmetric cross-entropy:

```python
# Both directions must see the full N×N matrix
logits = image_feats @ text_feats.T * logit_scale.exp()   # (N, N)

# Image-to-text: each image must find its text among all N texts
loss_i2t = cross_entropy(logits, targets)    # targets = [0,1,2,...,N-1]

# Text-to-image: symmetric
loss_t2i = cross_entropy(logits.T, targets)

loss = (loss_i2t + loss_t2i) / 2
```

The denominator of the softmax is Σ_j exp(sim(i,j)/τ), a sum over all N pairs in the batch. This is a global normalization: to compute the loss for one image, you need the similarity scores against every text in the batch at the same time.

This creates a hard distributed training constraint. With the batch spread across K GPUs:

```
GPU 0 has: images [0..N/K-1] and texts [0..N/K-1]
But to compute loss for image 0, it needs sim(image_0, text_j) for ALL j including j on GPU 1, GPU 2, etc.
→ AllGather both image and text embeddings across all GPUs
→ 2 AllGather operations per step
→ All GPUs idle while waiting for the full gather
```

CLIP passes both image and text features between all GPUs to compute the N×N normalization matrix, which costs two all-gather operations.

**SigLIP: sigmoid binary loss**

Unlike standard contrastive learning with softmax normalization, the sigmoid loss operates solely on image-text pairs and does not require a global view of the pairwise similarities for normalization ([Zhai et al., 2023](#ref-siglip)).

Each pair is an independent binary classification:

```python
# For every (image_i, text_j) pair in the batch:
# y_ij = +1 if i==j (matching), -1 if i!=j (non-matching)

logits = image_feats @ text_feats.T * t + b
# t = learnable temperature scalar, b = learnable bias scalar

# Binary cross-entropy per pair: no normalization needed
loss = -log(sigmoid(y_ij * logit_ij)).mean()
# = sum of N^2 independent sigmoid losses
```

There's no denominator requiring a global sum. The loss for pair (i,j) depends only on sim(image_i, text_j), nothing else. This means:

```
GPU 0 has: images [0..N/K-1] and texts [0..N/K-1]
GPU 0 computes sigmoid loss for all pairs it has locally
Only text features need to be gathered (to compute cross-GPU negative pairs)
→ Only 1 AllGather operation (texts only)
→ No softmax normalization barrier
```

SigLIP requires only a single all-gather operation for text features, which is cheaper than CLIP's two all-gather operations. However, an all-gather operation is still expensive because all GPUs stay idle while waiting to receive all features.

The practical consequence: SigLIP performs best at batch size 32K, whereas the softmax loss required 98K for optimal performance and still didn't outperform the sigmoid-based variant. SigLIP reaches peak performance at a much smaller batch size, making it significantly more accessible to train.

#### Part 2: the SigLIP-2 training recipe

SigLIP-2 extends the original image-text training objective with several prior, independently developed techniques into a unified recipe: captioning-based pretraining, self-supervised losses (self-distillation, masked prediction), and online data curation ([Tschannen et al., 2025](#ref-siglip2)).

This is the key departure from all CLIP-style models (OpenCLIP, DFN, SigLIP-v1). OpenCLIP and DFN train with one objective: contrastive loss. SigLIP-2 trains with four objectives simultaneously:

```
Loss_total = sigmoid_loss (100%)
           + LocCa_loss  (100%)      ← captioning decoder
           + SILC_loss   (last 20%)  ← self-distillation
           + masked_pred (last 20%)  ← masked prediction
```

**LocCa: captioning decoder for localization**

A standard transformer decoder with cross-attention is attached to the un-pooled vision encoder representation (before applying the MAP head). The decoder follows the shapes of the text encoder except that cross-attention layers are added and the number of layers is reduced by a factor of two. Besides image captioning, LocCa also trains for automatic referring expression prediction and grounded captioning. The former amounts to predicting bounding box coordinates for captions describing specific image regions, whereas the latter involves predicting region-specific captions given bounding box coordinates ([Tschannen et al., 2025](#ref-siglip2)).

This trains the **patch-level** features of the ViT (not just the pooled representation) to carry localization information. An OpenCLIP model optimizes only the pooled CLS token for contrastive alignment, so the individual patch features are useful but never directly supervised. LocCa forces patch features to encode where things are in the image, which dramatically improves OCR and dense visual tasks.

The decoder is only used during training and isn't released as part of the checkpoint; it's purely a training-time regularizer.

**SILC/TIPS: self-distillation and masked prediction**

Following SILC and TIPS, local-to-global correspondence learning is added with self-distillation and masked prediction losses to improve the local semantics of the un-pooled feature representation. The first term is the local-to-global consistency loss, in which the vision encoder becomes the student network getting a partial (local) view of the training image, trained to match the teacher's representation derived from the full image. The teacher parameters are obtained as an exponential moving average of the student parameters. The second loss term is the masked prediction objective: 50% of embedded image patches are replaced with mask tokens, training the student to match the features of the teacher at masked locations ([Tschannen et al., 2025](#ref-siglip2)).

This is the same technique as DINO/DINOv2 applied on top of SigLIP training. It improves the spatial/dense features of the patch tokens, making them useful for segmentation, depth estimation, and fine-grained grounding, capabilities that contrastive training alone doesn't strongly optimize.

#### Part 3: architecture, SO-400M vs ViT-bigG-14

From the actual configs:

|  | **OpenCLIP ViT-bigG-14** | **SigLIP-2 SO-400M** |
| --- | --- | --- |
| Parameters | ~1.9B | ~400M |
| Width (hidden) | 1664 | 1152 |
| Layers | 48 | 27 |
| Heads | 16 | 16 |
| Head dim | 104 | 72 |
| MLP intermediate | ~8193 (ratio 4.9231) | 4304 (ratio ~3.73) |
| Patch size | 14 | 14 |
| Activation | QuickGELU | GELU |
| Normalization | LayerNormFp32 | LayerNorm |
| Pooling | CLS token | MAP head |
| Pos embedding | Learned absolute | Learned absolute |
| Training loss | Softmax contrastive | Sigmoid + LocCa + SILC + masked pred |

**SO-400M ("shape optimized")**: the 400M parameter count comes from a non-standard depth/width ratio found via compute-optimal scaling laws. Standard ViT-L is wider (1024) and deeper (24 layers). SO-400M is narrower (1152 at 27 layers) but achieves better performance per FLOP than either ViT-L or ViT-H at comparable compute budgets. SoViT-400M achieves 90.3% fine-tuning accuracy on ImageNet and 82.2% zero-shot accuracy in the LiT setup ([Alabdulmohsin et al., 2023](#ref-sovit)).

**MAP head vs CLS token**

SigLIP-2 uses MAP (Multihead Attention Pooling) for its pooled output. This is functionally similar to the AttentionalPooler in CoCa: a small cross-attention module with one or a few learned queries attending to all patch tokens. Vision and text representations are pooled using a MAP head (attention pooling) ([Tschannen et al., 2025](#ref-siglip2)).

The difference from CLS token: CLS accumulates information during the transformer forward pass through self-attention with patches. MAP reads out from the final patch representations externally. MAP tends to produce better pooled representations for VLMs because the transformer body can focus purely on building good patch features without devoting capacity to the CLS aggregation task.

#### Part 4: which SigLIP-2 features Qwen3-VL actually uses

Qwen3-VL takes SigLIP-2 weights and modifies them for dynamic resolution. Some SigLIP-2 features are preserved, some are replaced:

```
SigLIP-2 feature          Qwen3-VL usage
─────────────────────────────────────────────
ViT backbone weights      ✅ initialized from
Sigmoid training          ✅ already baked into weights
LocCa supervision         ✅ baked in (patch features already localization-aware)
SILC/masked pred          ✅ baked in (dense features improved)
Learned absolute pos emb  ⚠️  interpolated (CoMP method) + 2D-RoPE added
MAP head                  ❌ replaced by Qwen3-VL's MLP merger
Fixed resolution          ❌ replaced by dynamic resolution
Multilingual text tower   ❌ not used (Qwen3-VL has its own LLM)
```

The critical point: Qwen3-VL inherits the superior patch-level features from SigLIP-2's LocCa and self-distillation training even though those training components are not active at Qwen3-VL inference time. The weights already encode the spatial awareness and dense feature quality baked in by multi-objective pretraining.

#### Part 5: why this matters vs DFN and OpenCLIP

The progression across the Qwen-VL lineage:

```
Qwen-VL:    OpenCLIP ViT-bigG    (softmax contrastive only)
Qwen2-VL:   DFN ViT-H-14        (softmax contrastive, but better curated data)
Qwen2.5-VL: Custom ViT          (CLIP-style training from scratch)
Qwen3-VL:   SigLIP-2 SO-400M    (sigmoid + captioning + self-distillation)
```

Each step improved data quality or training signal quality. SigLIP-2 represents a qualitative jump: it's the first encoder in the Qwen-VL lineage that was trained with objectives directly optimizing dense/spatial features (LocCa, masked prediction). This aligns well with Qwen3-VL's stated goals of strong grounding, OCR, document parsing, and fine-grained visual reasoning, all of which benefit from patch-level features that encode location, not just semantics.

The size reduction also matters: at 400M params vs 1.9B (OpenCLIP bigG) or 675M (Qwen2-VL's DFN ViT), SigLIP-2 SO-400M is more efficient while delivering better spatial features, freeing capacity budget for larger LLM backbones.

### Interleaved M-RoPE: fixing the spectral imbalance

This is the most technically precise architectural change.

**Qwen2.5-VL MRoPE (chunked):** the head dimension is split into three contiguous thirds:

```
dims [0 : D/3]      → temporal frequencies
dims [D/3 : 2D/3]   → height frequencies
dims [2D/3 : D]     → width frequencies
```

Each subspace covers a different range of frequency bands. The temporal subspace gets the first D/3 dimensions, which in RoPE correspond to the lowest frequencies (the slowest-varying sinusoids), and the width subspace gets the last D/3 dimensions, the highest frequencies. So temporal position is encoded mostly with low-frequency sinusoids, and spatial position with high-frequency ones. They are not in the same frequency regime.

**Why this is a problem:** Chunking the embedding dimensions into temporal, horizontal, and vertical groups induces an imbalanced frequency spectrum, which subsequent studies have shown to degrade performance on long-video understanding benchmarks. Specifically: temporal position needs both low frequencies (to distinguish far-apart frames) and high frequencies (to distinguish adjacent frames). When temporal gets only the lowest-frequency band, the model cannot precisely distinguish nearby frames. The same applies to spatial axes ([Qwen Team, 2025](#ref-qwen3vl)).

**Qwen3-VL Interleaved MRoPE (interleaved):** instead of contiguous chunks, t/h/w dimensions are interleaved across the full frequency spectrum:

```python
# Chunked (Qwen2.5-VL):
# dim 0,2,4,...,D/3-2   → temporal
# dim D/3,...,2D/3-2    → height
# dim 2D/3,...,D-2      → width

# Interleaved (Qwen3-VL):
# dim 0,6,12,...  → temporal   (every 3rd dim starting at 0)
# dim 2,8,14,...  → height     (every 3rd dim starting at 2)
# dim 4,10,16,... → width      (every 3rd dim starting at 4)
```

Each axis now gets dimensions evenly distributed across all frequency bands, both low and high. The dot product between two tokens encodes relative temporal distance at all frequencies, not just the low ones. This substantially improves the model's ability to distinguish both coarse (seconds apart) and fine (milliseconds apart) temporal relationships.

```python
# Interleaved MRoPE application
def apply_interleaved_mrope(q, k, t_ids, h_ids, w_ids, head_dim):
    # interleave: dims 0,3,6,... for t; 1,4,7,... for h; 2,5,8,... for w
    q_t = q[..., 0::3]   # temporal dims
    q_h = q[..., 1::3]   # height dims
    q_w = q[..., 2::3]   # width dims

    q[..., 0::3] = rotate(q_t, cos_t, sin_t)
    q[..., 1::3] = rotate(q_h, cos_h, sin_h)
    q[..., 2::3] = rotate(q_w, cos_w, sin_w)
    # same for k
```

### DeepStack

DeepStack ([Meng et al., 2024](#ref-deepstack)).

In every VLM since LLaVA, visual tokens flow into the LLM at exactly one point:

```
image → ViT (32 layers) → merger → [vis_tok_0, vis_tok_1, ..., vis_tok_N]
                                             ↓
                                     LLM Layer 0 processes all N tokens
                                     LLM Layer 1 processes all N tokens
                                     ...
                                     LLM Layer 32 processes all N tokens
```

Most large multimodal models are implemented by feeding visual tokens as a sequence into the first layer of a large language model. The resulting architecture is simple but significantly increases computation and memory costs, as it has to handle a large number of additional tokens in its input layer.

This has two problems:

**1. Context length bottleneck**: all visual tokens must fit in the input sequence. Adding more visual tokens for higher resolution or longer video directly increases the quadratic attention cost across all LLM layers.

**2. Single-point injection**: the LLM receives visual information only at layer 0. After that, visual features have to propagate through the entire transformer via attention, which is a lossy, indirect process. The LLM's upper layers, which do most of the complex reasoning, end up working with visual features that have been compressed and transformed through 32 layers of text-centric attention.

DeepStack is a versatile strategy that provides finer-grained visual information without increasing the visual context length. It achieves this by dividing image feature extraction into two streams: a global-view stream that captures global information, and a high-resolution stream that enhances the global information by stacking dilated high-resolution image features across different layers of the LLMs.

The original DeepStack works as follows:

```
Input: LOW-RES image + HIGH-RES image (same image at two resolutions)

Low-res path:   LR_image → ViT → merger → vis_tokens (short, standard input)
High-res path:  HR_image → ViT → merger → stack of spatial patches (divided into N groups)
```

The high-res features are divided into N groups along the spatial dimension:

```python
# Original DeepStack pseudocode (from paper)
def forward(H0, Xstack, lstart, n, vis_pos):
    H = H0   # initial hidden states, includes vis_tokens from low-res
    for idx, TransformerLayer in enumerate(self.layers):
        # Before each target layer, add the next spatial group
        if idx >= lstart and (idx - lstart) % n == 0:
            H[vis_pos] += Xstack[(idx - lstart) // n]
        H = TransformerLayer(H)
```

Xstack contains spatially different patches from the high-res image, injected one group per layer. The key is `H[vis_pos] +=`, an additive residual to the existing visual token positions. No new tokens are added to the sequence; the existing visual token representations are just enriched between layers.

What "spatially different patches" means: the high-res image is divided into a 2D grid of tiles. Group 0 = top-left neighbors, Group 1 = top-right neighbors, etc. Each group captures a different spatial region of the image at high resolution. Considering the 2D nature of images, neighbors from the high-resolution version are extracted and reorganized into DeepStack, which are then fed to the consequent layers in LLMs.

Unlike the original DeepStack approach, which stacks tokens from multi-scale visual inputs, Qwen3-VL extends DeepStack to extract visual tokens from intermediate layers of the Vision Transformer. This design preserves rich visual information, ranging from low- to high-level representations. Specifically, features are selected from three distinct levels of the vision encoder. Dedicated vision-language merger modules project these multi-level features into visual tokens, which are then added directly to the corresponding hidden states of the first three LLM layers.

The comparison:

```
Original DeepStack:
  Source of multi-level features: SPATIAL (different tiles of a high-res image)
  Multiple mergers: Yes
  Injection mechanism: additive residual to vis_pos in LLM

Qwen3-VL DeepStack:
  Source of multi-level features: DEPTH (different ViT layers of the SAME image)
  Multiple mergers: Yes (one per level)
  Injection mechanism: additive residual to first 3 LLM layer hidden states
```

Concretely:

```python
# ViT forward pass with intermediate feature extraction
def vit_forward_with_deepstack(x):
    for i, block in enumerate(self.blocks):   # 32 blocks (SigLIP-2)
        x = block(x)
        if i == 10:   level1_feats = x.clone()   # early features
        if i == 21:   level2_feats = x.clone()   # mid features
    level3_feats = x                              # final features (standard path)
    return level1_feats, level2_feats, level3_feats

# Three dedicated mergers
vis_tokens_final  = merger_3(level3_feats)   # standard path → LLM input
vis_tokens_early  = merger_1(level1_feats)   # early features → LLM layer 1 injection
vis_tokens_mid    = merger_2(level2_feats)   # mid features   → LLM layer 2 injection

# LLM forward pass with DeepStack injection
def llm_forward_with_deepstack(H, vis_pos):
    for idx, layer in enumerate(self.layers):
        if idx == 1:
            H[vis_pos] += vis_tokens_early   # inject early ViT features
        if idx == 2:
            H[vis_pos] += vis_tokens_mid     # inject mid ViT features
        H = layer(H)
    return H
```

#### Why intermediate ViT layers: the representation hierarchy

The motivation is grounded in what different ViT layers encode. This has been well-studied in ViT interpretability research:

```
ViT layers 0–7:    local, low-level features
  - edge detectors, oriented gratings, blob detectors
  - color channels, spatial frequency bands
  - very similar to early CNN layers

ViT layers 8–20:   mid-level structural features
  - shape primitives (corners, junctions, curves)
  - object parts (eyes, wheels, characters in text)
  - relative spatial relationships

ViT layers 21–32:  high-level semantic features
  - object identity and category
  - scene-level context
  - cross-patch semantic grouping
```

The standard LLM pipeline only receives layer-32 features, which are pure semantics. For tasks that require low-level precision:

**OCR**: recognizing characters requires pixel-level detail. A character "a" vs "o" differs by one small stroke. Layer-32 features have collapsed this distinction into abstract "letter" representations. Layer 10 features still retain the stroke-level detail.

**Grounding**: localizing "the third word in the second line" requires knowing exact spatial positions of strokes, not semantic labels.

**Fine-grained attribute recognition**: "red car with a dent near the left headlight", where the dent detection needs edge-level features, not semantic "car" features.

By injecting early features (layer 10) and mid features (layer 21) into LLM layers 1 and 2, the LLM can access these lower-level representations directly at the early stages of its own forward pass, where lower-level information is most useful.

#### Why additive residual, not concatenation

The critical design choice is `H[vis_pos] +=` rather than extending the sequence. The two alternatives would be:

**Concatenation (what you'd naively do):**

```python
# WRONG: blows up context length
H = concat([vis_tokens_final, vis_tokens_early, vis_tokens_mid, text_tokens])
# 256 vis + 256 early + 256 mid + L text = L + 768 tokens → 3× longer sequence
# Quadratic attention cost: (L + 768)² >> L²
```

Token replacement (another option):

```python
# Would discard previous computation
H[vis_pos] = vis_tokens_early   # loses the information already processed
```

Additive residual (what DeepStack uses):

```
H[vis_pos] += vis_tokens_early   # accumulates new information on top of existing
```

The additive residual is elegant because it respects the transformer's residual stream philosophy. Each LLM layer has already computed its contribution to the hidden state. The DeepStack injection adds new visual information into that stream without erasing prior computation. The visual token hidden states at position vis_pos accumulate:

```
After LLM layer 0:  H[vis_pos] = layer_0(input_vis_tokens)
                    H[vis_pos] += merger_1(ViT_level1)        ← early ViT enrichment
After LLM layer 1:  H[vis_pos] = layer_1(H[vis_pos])
                    H[vis_pos] += merger_2(ViT_level2)        ← mid ViT enrichment
After LLM layer 2:  H[vis_pos] = layer_2(H[vis_pos])
Layers 3–32:        H[vis_pos] = standard (no more enrichment)
```

Context length stays exactly the same as without DeepStack. Only the hidden state values at visual token positions change.

Each level gets its own merger module because the features at different ViT depths have different statistical properties:

```python
class DeepStackMerger(nn.Module):
    """Each level has its own dedicated 2-layer MLP"""
    def __init__(self, vit_hidden=1152, llm_hidden=3584, spatial_merge=2):
        super().__init__()
        # same 2×2 spatial merger as standard path
        # input: 4 adjacent patches concatenated
        self.mlp = nn.Sequential(
            nn.Linear(vit_hidden * spatial_merge * spatial_merge, llm_hidden),
            nn.GELU(),
            nn.Linear(llm_hidden, llm_hidden)
        )

    def forward(self, vit_feats, grid_h, grid_w):
        # spatial 2×2 merge
        x = vit_feats.reshape(B, grid_h // 2, 2, grid_w // 2, 2, C)
        x = x.permute(0, 1, 3, 2, 4, 5).reshape(B, -1, 4 * C)
        return self.mlp(x)   # (B, grid_h//2 * grid_w//2, llm_hidden)

# Three instantiations: separate weights
merger_1 = DeepStackMerger()  # for level 1 (early ViT, layer 10)
merger_2 = DeepStackMerger()  # for level 2 (mid ViT, layer 21)
merger_3 = DeepStackMerger()  # for level 3 (final ViT, standard path)
```

Separate weights are important: the projection from layer-10 features to LLM space needs a different linear mapping than the projection from layer-32 features. Layer-10 features are raw, low-level, and have very different statistics, so projecting them with the same weights as layer-32 features would be like using the same transform for pixel intensities and object embeddings.

### Text-based Timestamps

Up through Qwen2.5-VL, video time was encoded through the temporal axis of M-RoPE. I'll call that T-RoPE (the time component of the rotary encoding): every frame gets a temporal position ID, and the model is supposed to learn what a given gap in those IDs means in seconds. Qwen3-VL drops that scheme and instead writes timestamps straight into the token stream as text, e.g. `<45.0 seconds>` between frames. The rest of this section is about why T-RoPE struggles and why plain text fixes it.

#### T-RoPE problem 1: position ID sparsity at inference

To understand exactly why large, sparse position IDs break T-RoPE, recall that RoPE encodes position by rotating Q and K vectors with sinusoidal functions at frequency `θ_d = 1 / (base^(2d/dim))`. The model's attention weights learn to respond to specific patterns of relative temporal distances, encoded as differences in rotation angle.

During training, if videos are mostly short (common in practice, since most video datasets are clips of 30 to 120 seconds), the temporal IDs seen during training are bounded:

```
Training distribution (2 FPS, 0.5s time unit):
  30s clips → t_ids 0 to 60
  2min clips → t_ids 0 to 240
  Most training → t_ids 0 to ~500
```

At inference on a 2-hour video:

```
t_ids span 0 to 14,400
```

RoPE does produce sinusoidal values for t_id=14,400, but the model's weight matrices were never shaped by gradients at those positions. The effective attention patterns, which learned that "frames 5 apart in time should attend differently than frames 50 apart", break down because the learned weights assume a certain range of rotation angles.

The "sparse" part compounds this. With dynamic FPS sampling (Qwen2.5-VL's addition), if a video is sampled at 0.5 FPS instead of 2 FPS, consecutive frames get t_ids like 0, 4, 8, 12... instead of 0, 1, 2, 3... The model has to generalize "gap of 4 in t_id means 2 seconds elapsed", but it was trained mostly on "gap of 1 means 0.5 seconds." The relative distance signal is the same mathematically, but the model hasn't seen that pattern in training.

#### T-RoPE problem 2: training data requirements

For T-RoPE to generalize across the full range of t_ids you want at inference, the training data must contain videos spanning that full range at diverse sampling rates. Specifically:

- Long videos (hours) are rare in high-quality annotation datasets
- Uniform sampling across frame rates requires curating many versions of each video at different FPS
- The model needs to see t_id=7200 during training to know how to handle it at inference
- This imposes specific data collection constraints that are expensive to satisfy

Text timestamps have no such requirement. The model already understands `7200` as a number from its text pretraining on billions of documents containing numbers of all magnitudes. `<7200 seconds>` is semantically equivalent to writing "at the two hour mark", which is information the model can reason about directly.

T-RoPE encodes temporal position **implicitly**, baked into the geometry of Q and K vector rotations, so the model can't inspect or reason about its own positional encodings during generation.

Text timestamps encode temporal position **explicitly**, as readable tokens in the context window. This has several consequences:

**Chain-of-thought temporal reasoning becomes possible.** In Qwen3's thinking mode, the model can explicitly reference timestamps in its reasoning:

```
<think>
The question asks what happens between the 30 and 45 second marks.
At <30.0 seconds> I can see the character approaching the door.
At <45.0 seconds> the door is already open.
The door must have been opened between these timestamps...
</think>
```

This is architecturally impossible with T-RoPE: the temporal information is embedded in positional-encoding geometry that the model can't inspect or manipulate in generated text.

**Temporal grounding answers are directly supervised.** When the model generates "this happens at 45.0 seconds", the correct answer "45.0 seconds" is a text string that can be directly compared against a ground truth label. T-RoPE temporal information never appears in the output; it only influences attention patterns. Training with explicit timestamp supervision gives a direct gradient signal for temporal localization accuracy.

**Format flexibility at no extra cost.** The paper notes training on both seconds and HMS formats:

```
<45.0 seconds>   ← decimal seconds format
<00:00:45>        ← HMS format
```

A 2-hour video timestamp in HMS is <02:03:47>, still about 5 tokens, and the model understands the format from having seen timecodes in its pretraining data (YouTube transcripts, subtitles, video descriptions). T-RoPE has no equivalent mechanism for format diversity; it's purely a positional encoding.

## Qwen3.5 (2026)

**There is no "Qwen3.5-VL" as a separate model.** Qwen3.5 is a native vision-language foundation model: it folds the previously separate Qwen3 text models and Qwen3-VL vision-language models into a single family through early-fusion training on multimodal tokens. The "VL" suffix disappears entirely. This matters because, up to this point, the text backbone was always trained separately and then we bolted the vision tower on top.

### Early Fusion

#### What "early fusion" actually means: training paradigm vs architecture

The confusion comes from two different meanings of "early fusion" in the literature:

**Architectural early fusion** (Chameleon, Emu3): image pixels are discretized into codebook tokens by a VQ-VAE, added to the vocabulary, and the LLM processes them as regular tokens with no separate ViT tower at all. The vision encoding is literally inside the embedding table.

**Training early fusion** (Qwen3.5): the ViT + merger + LLM structure is preserved, but the entire system is trained jointly on multimodal data from the very first pretraining step; the vision encoder never exists as an independently trained CLIP-style model.

Rather than attaching a separate vision encoder to a text model as an afterthought, Qwen3.5 trains on text and image tokens together from the beginning. This can enable stronger reasoning over diagrams, charts, and documents compared to prior Qwen3-VL models, which used a separate vision pipeline.

Qwen3.5 is the training-paradigm kind. It employs early-fusion multimodal training, where image patches, audio spectrograms, and tokenized text are all projected into a shared latent space before entering the transformer backbone.

#### The late-fusion problem it's solving

To understand why this matters, trace the lifecycle of components in Qwen3-VL:

```
SigLIP-2 vision encoder lifecycle:
  Step 1: Trained on WebLI (10B image-text pairs)
          Objectives: sigmoid contrastive + LocCa captioning + SILC self-distillation
          Result: encoder optimized to produce general visual representations
  Step 2: Loaded as Qwen3-VL's vision encoder
          Weights modified: absolute pos embed → 2D-RoPE
  Step 3: Continued training with Qwen3-VL's vision-language objectives
          But it starts from a checkpoint shaped by CLIP-style objectives

Qwen3 LLM lifecycle:
  Step 1: Trained on text-only corpus
          Result: LLM with no visual experience
  Step 2: Vision encoder attached, alignment training begins
          LLM learns to interpret visual tokens it has never seen before
```

The structural seam between two independently-trained systems creates alignment friction. The vision encoder speaks a language (visual feature space) it developed alone, and the LLM has to learn to read that language. No matter how good the merger or how long the alignment training, there's a representation mismatch baked in from the start.

With early fusion:

```
Qwen3.5 lifecycle:
  Step 1 (day 1 of pretraining): entire system trained on text + images simultaneously
          ViT, merger, and LLM all initialized randomly (or with compatible inits)
          All parameters receive gradients from both text and vision examples
          The vision encoder develops representations jointly with the LLM's needs
          The LLM develops its hidden states with visual information present from the start
```

The vision encoder never knew a world without language. The LLM never knew a world without images. They co-evolve together.

Comparing Qwen3.5's vision_config to SigLIP-2 SO-400M:

| **Config field** | **SigLIP-2 SO-400M** | **Qwen3.5 (35B)** |
| --- | --- | --- |
| depth | 27 | 27 |
| hidden_size | 1152 | 1152 |
| num_heads | 16 | 16 |
| intermediate_size | 4304 | 4304 |
| patch_size | 14 | **16** |

The ViT shape is identical to SigLIP-2 SO-400M, but patch_size changes from 14→16. This has one concrete effect: for a 224px image, patch_size=14 gives 16×16=256 patches, while patch_size=16 gives 14×14=196 patches. Fewer, larger patches → fewer visual tokens → cheaper attention in the LLM. The trade-off: slightly less spatial resolution per patch, but more efficient processing.

`temporal_patch_size: 2`: the same 3D convolution inherited from Qwen2-VL and Qwen3-VL for video, where pairs of adjacent frames are merged temporally into a single patch token.

`spatial_merge_size: 2`: the same 2×2 MLP merger, with 4 adjacent patches concatenated and projected.

`out_hidden_size: 2048`: the merger projects into 2048 dims for the 35B model. For comparison, Qwen3-VL-32B would have `out_hidden_size` matching its LLM hidden dim. The early-fusion training means this projection is learned in direct response to what the LLM needs from day 1.

**DeepStack is removed:** `deepstack_visual_indexes: []`

This is the most significant architectural change visible in the config. The vision component still uses a DeepStack-style Vision Transformer with Conv3d patch embeddings, where features can be merged from multiple transformer layers rather than only the final layer.

But the actual config shows `"deepstack_visual_indexes": []`, an empty list, which means **no intermediate ViT layers are injected into the LLM**.

This makes sense in the context of early fusion. Recall why DeepStack was added in Qwen3-VL: the SigLIP-2 encoder was pretrained with a CLIP-style objective that optimized the final-layer representation, leaving intermediate layers under-utilized for the LLM's needs. DeepStack compensated by injecting early and mid-layer ViT features into the first LLM layers to recover low-level spatial information that the final-layer pooling had discarded.

With early fusion, this problem doesn't exist. The ViT's final-layer features are co-optimized with the LLM's needs throughout training: the LLM's loss directly shapes what the ViT's last layer should encode. Low-level features don't need to be re-injected from intermediate layers because the entire ViT learns to preserve whatever the LLM needs in its final output. DeepStack was a workaround for a mismatch that early fusion eliminates at the source.

In late fusion (Qwen3-VL), the vision encoder and LLM have two separate representation spaces. The merger is a bridge:

```
ViT representation space (shaped by CLIP training)
    ↓  [merger: projection + 2×2 spatial merge]
LLM representation space (shaped by text training)
```

The merger must learn to translate between two foreign spaces. Its weights are the only mechanism bridging two independently-shaped manifolds.

In early fusion, from the first training step:

```python
# Conceptually, gradients flow back through both components
loss = language_model_loss(output)

# Gradient to LLM: shapes how LLM processes visual tokens
dloss/d(LLM_weights)

# Gradient through LLM → merger → ViT: shapes what the ViT encodes
dloss/d(merger_weights)
dloss/d(ViT_weights)
```

The ViT is not encoding "whatever SigLIP thinks is a good visual representation." It's encoding whatever the LLM finds useful for generating the next token. These are related but not identical objectives: a CLIP model maximizes global image-text alignment, while an LLM needs dense spatial information, fine-grained attributes, positional relationships, and temporal dynamics. Early fusion trains the ViT to optimize for what the LLM actually needs.

### Hybrid Gated DeltaNet

The other big change in Qwen3.5 is on the language side: instead of full softmax attention in every layer, most layers use Gated DeltaNet, a linear-attention block, with full attention sprinkled in. Gated DeltaNet didn't appear out of nowhere, so it's worth building up to it from the bottom. There are three predecessor mechanisms, and each one is insufficient on its own.

#### Part 1: standard linear attention

Standard softmax attention computes:

$$
\operatorname{attn}(Q,K,V) = \operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d}}\right)V
$$

The denominator of the softmax forces each output to be a normalized weighted sum across all keys, and that's the O(N²) bottleneck.

The key algebraic trick: replace softmax with a kernel feature map φ, so that

$$
\operatorname{softmax}(q_t^\top k_i) \approx \phi(q_t)^\top \phi(k_i)
$$

This factorizes the attention score into an inner product of two vectors. Now you can reorder the summation:

$$
o_t = \frac{\sum_i \phi(q_t)^\top \phi(k_i) \cdot v_i}{\sum_i \phi(q_t)^\top \phi(k_i)} = \frac{\phi(q_t)^\top\left(\sum_i \phi(k_i)v_i^\top\right)}{\phi(q_t)^\top\left(\sum_i \phi(k_i)\right)}
$$

The parenthesized terms don't depend on t, so they can be accumulated incrementally. This gives you the **recurrent form**:

$$
S_t = S_{t-1} + v_t k_t^\top \qquad \text{(state update)}
\\
o_t = S_t q_t \qquad \text{(readout)}
$$

where `S_t` is a matrix-valued hidden state. **Intuition for S_t**: think of St as an associative memory.

**Complexity gains**:

- Training: still O(N·d²), but avoids materializing the N×N matrix
- Inference: **O(1) per token**, just maintain `S_t` and update it

**The fatal flaw**: `S_t` is unbounded and never forgets. Every rank-1 write accumulates forever. After many tokens, the state matrix is the sum of thousands of outer products, and it saturates. Old, irrelevant associations bleed into every future query, so the signal-to-noise ratio degrades catastrophically on long sequences.

#### Part 2: Mamba2, adding a forget gate

Mamba2 ([Dao & Gu, 2024](#ref-mamba2)) extends linear attention with a scalar, data-dependent decay:

$$
S_t = \alpha_t S_{t-1} + v_t k_t^\top
$$

The scalar gate gives the model a global "reset" control:

| **αt value** | **Behavior** |
| --- | --- |
| αt→1 | Keep everything, pure accumulation (≈ plain linear attention) |
| αt→0 | Wipe the state, start fresh from this token |
| αt≈0.9 | Exponential decay, old memories fade gradually |

This directly solves the **saturation problem** from plain linear attention. The state no longer grows unboundedly; old rank-1 writes are exponentially discounted over time.

**Intuition**: think of αt as a "how much do I trust my memory right now?" knob. When the model hits a topic shift, say a new document boundary or a semantic discontinuity, it can learn to emit a small $\alpha_t$ and effectively flush the state.

If the model needs to forget a specific key-value association, all of them get forgotten equally, which makes the process blunt.

The scalar αt applies the same decay to every dimension of the state uniformly. You can't tell it "forget just the fact about Paris but keep the fact about Berlin." Mamba2 adds the ability to forget, but the forgetting is coarse-grained. The next natural question is whether we can make the write operation itself smarter, so that new information **replaces** specific old associations instead of decaying everything uniformly.

#### Part 3: DeltaNet, smarter writes

Mamba2 lets the model forget, but it forgets everything at once. DeltaNet ([Yang et al., 2024](#ref-deltanet)) attacks the write side instead. The idea comes from the classic delta rule (Widrow-Hoff): before writing a new key-value pair, you first look up what the state currently predicts for that key, and you only write the difference.

Plain linear attention writes `S_t = S_{t-1} + v_t k_t^T`, blindly stacking the new pair on top of whatever was already there. DeltaNet instead computes the current prediction for key `k_t`, which is `S_{t-1} k_t`, takes the error against the target `v_t`, and writes a correction scaled by a per-token learning rate `β_t`:

$$
S_t = S_{t-1} + \beta_t\,(v_t - S_{t-1} k_t)\,k_t^\top
$$

If we assume `k_t` is unit-norm, this rearranges into a form that makes the behavior obvious:

$$
S_t = S_{t-1}\left(I - \beta_t\,k_t k_t^\top\right) + \beta_t\,v_t k_t^\top
$$

The `(I - β_t k_t k_t^T)` term erases the part of the state that lies along `k_t`, and then `β_t v_t k_t^T` writes the fresh association back in. So a write for "Paris" overwrites the old "Paris" entry without touching "Berlin". This is exactly the targeted update Mamba2 couldn't do: forgetting is now per-association rather than global.

The catch is that DeltaNet has no global decay. Anything you never write to again sticks around forever, just like plain linear attention. It fixed the precision of writes but gave up the ability to let stale memory fade on its own.

#### Part 4: Gated DeltaNet, decay plus the delta rule

Gated DeltaNet ([Yang et al., 2024](#ref-gateddeltanet)) is the obvious synthesis: keep Mamba2's scalar forget gate `α_t` *and* DeltaNet's targeted delta-rule write. The update is

$$
S_t = S_{t-1}\,\alpha_t\left(I - \beta_t\,k_t k_t^\top\right) + \beta_t\,v_t k_t^\top
$$

Now the model has two independent knobs. `α_t` controls global forgetting, the same "how much do I trust my whole memory right now" dial from Mamba2, and `β_t` controls how aggressively the current key gets overwritten. Push `α_t → 1` and you recover DeltaNet (precise writes, no decay); push `β_t → 0` and you recover Mamba2 (global decay, no targeted writes). Gated DeltaNet sits in between and gets to use both, which is why it tends to beat either one alone on long-context recall.

#### Why "hybrid"

Gated DeltaNet is cheap, with an O(1) state per token at inference, and it's good at smoothly mixing information over long contexts. But its fixed-size matrix state is still a lossy summary, so it can't do the kind of exact, look-anything-up recall that full softmax attention gives you. So Qwen3.5 doesn't pick one or the other, it interleaves them: most layers are Gated DeltaNet, with full-attention layers dropped in periodically. This is the same trick we saw with window attention in the ViT, where a few full-attention layers act as global checkpoints among many cheap local ones. The Gated DeltaNet layers carry the long-range context efficiently, and the occasional full-attention layer is there for precise retrieval when the task actually needs it.

### Scaling Up

#### MoE configuration scales up dramatically

**Qwen3-VL 235B-A22B:** 128 experts total, 8 routed activated per token, ~22B activated.

**Qwen3.5 397B-A17B (flagship):** 512 experts with 10 routed + 1 shared expert activated per token, 397B total parameters with 17B activated per forward pass.

More experts (512 vs 128) but fewer activated parameters (17B vs 22B), so the model specializes more aggressively while staying cheaper per token.

The 35B-A3B model uses 256 experts with 8 routed + 1 shared, with only 3B activated, yet it's competitive with Qwen3-VL-235B on vision benchmarks at a fraction of the inference cost.

#### Vocabulary doubles

**Qwen3-VL:** 150K token vocabulary.

**Qwen3.5:** 248,320 token vocabulary (padded), with 15-25% lower token counts on technical datasets. The larger vocabulary improves tokenization efficiency, especially for code, mathematics, and multilingual content, which reduces sequence length and therefore compute cost for the same input.

#### Language coverage expands

**Qwen3-VL:** strong multilingual coverage.

**Qwen3.5:** expanded support to 201 languages and dialects, enabling inclusive, worldwide deployment.

#### RL scales to millions of agents

**Qwen3-VL:** RL applied in post-training for thinking/non-thinking variants.

**Qwen3.5:** reinforcement learning scaled across million-agent environments with progressively complex task distributions for robust real-world adaptability. The scale of RL training is orders of magnitude larger, and it specifically targets agentic tasks: GUI interaction, tool use, web browsing, and long-horizon planning.

Qwen3.5 is also agent-native: the separate "VL" and "coder" model lines are discontinued and folded into a single unified recipe.

## Wrapping Up

If there's one through-line across these five generations, it's the slow erasure of the seam between the vision encoder and the language model. We started with a frozen LLM reading a fixed 256-vector summary of an image, and we ended with one model trained on text and image tokens together from the first step. Here's the whole lineage at a glance:

| Generation | Vision encoder | Connector | Position encoding | Defining idea |
| --- | --- | --- | --- | --- |
| Qwen-VL | OpenCLIP ViT-bigG | Resampler (256 queries) | learned absolute | frozen LLM, fixed-size image summary |
| Qwen2-VL | DFN ViT-H | MLP merger | 2D RoPE / M-RoPE | dynamic resolution, images and video |
| Qwen2.5-VL | custom ViT (from scratch) | 2-layer MLP merger | M-RoPE, abs. time | window attention, SwiGLU/RMSNorm ViT |
| Qwen3-VL | SigLIP-2 SO-400M | MLP merger + DeepStack | interleaved M-RoPE | dense features, text timestamps |
| Qwen3.5 | co-trained ViT | MLP merger (no DeepStack) | interleaved M-RoPE | early fusion, Gated DeltaNet, MoE |

Each row is mostly a reaction to a limitation in the row above it. The Resampler's fixed token count gave way to dynamic resolution, dynamic resolution's quadratic cost forced window attention, the CLIP-style encoder's weak dense features motivated SigLIP-2 and DeepStack, and the structural seam of late fusion is what early fusion finally removes. Reading the lineage this way, each architectural choice stops looking arbitrary and starts looking like the obvious next move.
